Delta, Base, pull requests

Everything you would otherwise leave the app for: what changed, what it changed from, and where it is going.

Delta

⌘D. Three modes over the same selection:

ModeCompares
Taskthe task branch against its merge-base with the default branch — the whole change
Uncommittedthe working tree against HEAD — what the agent has not committed yet
Base vs originthe local branch against its remote — what is not pushed

Files are grouped by repository, with an add/modify/delete filter, a fuzzy filter field and per-file line counts. The mode is the menu in the section's header. Click a file to read its diff in the reading column beside the inspector; j/k move between files, [/] between hunks.

Files an agent mentions

⌘-click a path, or a file:// link, in a thread's terminal and the file opens in the same column, at the line it names: the task's copy while the thread belongs to a task, the base checkout's otherwise, the file itself when it lies elsewhere. A relative path is looked for from the thread's folder, then at the root of every repository of the task — agents often leave the repository's name out — and when several files match, the header lists them. A file the task changed has a button for its diff. Web links still open in the browser.

The diff

Native text: selectable, searchable with ⌘F, with both line numbers, and a copy / reveal / open-in-editor row for the file.

Commit, push, open the PR

That is the agent's work in its thread, so the buttons are off by default. With Settings ▸ Git ▸ Show commit and push buttons, Commit… and Push appear when the pointer is on the Delta header, and Create PR on the Pull Request header. Create PR shells out to gh and links the resulting pull request to the task, so the Pull Request section keeps showing it and its checks.

The box at the end of each file row marks it as viewed: the row dims, so what is left to read stands out. The mark lasts while the file's diff stays the one you looked at; as soon as the agent changes that file again, it clears itself.

Commenting on lines

Review the agent's work where you read it. In the diff, a + appears in the line-number gutter under the pointer: click it to comment on that line, or drag down the gutter to comment on a range. The comment editor opens under the lines (⌘↩ adds it). Comments show as tinted rows under the lines they cover; click one to edit or delete it, or open the list from the review strip at the foot of the inspector.

Comments are kept per task, under ~/.scope/reviews/ — never in the sandbox. Each remembers the exact text of its first line and three lines around it, so it follows the code as the agent keeps editing: a comment whose lines are gone is listed at the top of the file instead of pointing at the wrong place.

Send Review turns them into one message — per comment the file, the line numbers the file has now, the code around them and your text — and pastes it into the task's thread as a single input. With several threads running, pick one. If the thread is in the middle of a turn, the review waits and goes out as soon as its hooks say the turn ended. Sent comments are cleared.

Base

⇧⌘B. The repository as it is on disk, outside any sandbox — the reference the agent is working from.

  • Files — the tree of the checkout, every folder closed until you open it; a file opens read-only, with line numbers, in the reading column.
  • Search — git grep across the checkout, with case, regex, whole-word and folder filters. A result opens in the reading column and opens just the folders above it in Files.
  • History — recent commits of the branch.

Pull sits in the Base header as soon as origin is ahead; it is fast-forward only and refuses on a dirty tree. Fetch, Open in Editor, Shell and Reveal come on hover. Shell opens a thread rooted at the base checkout — useful when you want to run something against the real branch rather than a sandbox.

Pull requests

⇧⌘P. Open pull requests of the selected repository, through the gh CLI and your existing GitHub authentication: title, number, author, branch, checks and review state. Open one in the browser, or turn it into a task whose sandbox sits on the PR's head.

The panel needs gh auth login and a GitHub remote. A repository without one simply shows nothing to list.

A task's pull request, to the merge

Once a task has a pull request — opened from its thread, or the one it was opened on — the Pull Request section lists its checks, refreshed every minute: state, name, and a link to each check's page.

  • Send to Thread on a failed check fetches the failed steps' log with gh run view --log-failed and pastes its end, with a sentence naming the check, into the task's thread — the same delivery as a review, so a thread mid-turn gets it when the turn ends. A check that is not a GitHub Actions job has no log to fetch; the thread gets its link.
  • Merge appears on the Pull Request header (with the commit and push buttons turned on) when GitHub says the pull request merges cleanly. It uses the method the repository allows (merge commit, else squash, else rebase), asks first, and then offers to close the task, which removes its sandboxes and deletes the branch the task created — never a branch name it would have to guess.
  • Fix Conflicts stays on the header when the pull request conflicts with its base: the thread is asked to merge the base into the branch, resolve, run the tests and push.

Every task, not only the one on screen

The task on screen is refreshed every minute; every other open task is read from GitHub every 5 minutes in the background, two gh calls at a time and spread over the interval. A task with nothing committed yet is skipped until it has a commit; one whose fetch fails is asked less and less often, up to once an hour; a merged or closed pull request every half hour. Nothing runs in Low Power Mode. The checks say how old they are — ✓ checks passed · 4 min ago — on the Pull Request header and in the task's hover card, and turn grey once older than 15 minutes: a green that old may no longer be true.

When a refresh sees the pull request merged and no thread of the task is running, Scope archives the task the way the sidebar's Archive does and leaves one quiet notice, Archived <task>: pull request merged, with Restore. A running thread postpones it to the next refresh. A pull request closed without merging never archives anything, and a task with a pull request that you restore stays open. Turn it off in Settings ▸ General ▸ Tasks ▸ Archive a task when its pull request merges. A task with a pull request therefore stays open until the merge: agents no longer poll GitHub for it, and only archive themselves work that has no pull request.

A task left open with no thread activity for 3 days (Settings ▸ General ▸ Tasks ▸ Idle after), or whose pull request was closed without merging, says so at the end of its row — idle 4d, PR closed — and, arranged by state, goes under Dormant, unless it is waiting for you or working.
