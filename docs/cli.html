Command line and MCP

Scope answers on the same socket its driver hooks use. scope is the command line into a running app; scope mcp is the same commands, spoken as MCP, so an agent can open a thread or sandbox a task on its own.

Getting scope

Inside a thread there is nothing to do: Scope puts its own Contents/Helpers first on the PATH it hands the driver, so scope and scope-hook are already there.

For your own terminal, Settings ▸ Automation ▸ Install links the tool into /usr/local/bin when that folder is writable, otherwise into ~/.scope/bin (it then tells you the line to add to your shell). The link points inside the app bundle, so an update moves with the app.

Commands

scope list [scopes|threads|tasks]   # what Scope is holding right now
scope thread new [options]          # open a thread, print its id (--task, --branch, --repo, --driver, --model, -p)
scope thread send <id> <text>       # type into it and press ↩ (--no-enter, --command, --wait)
scope thread read <id>              # the last lines of its terminal (-n, --cursor), or --reply
scope thread wait <id>...           # until they finish their turn; prints each last reply (--any)
scope thread stop <id>              # stop its process; the row stays
scope thread close <id>             # hang it up and remove it
scope task new <prompt> [options]   # branch + worktrees + first thread (--pr, --issue, --topic, --deliverable, --attempts)
scope task show <id|slug>           # its brief, and what was kept at archive: last answers, https://github.com/maastrich/scopeRT.md
scope task archive <id|slug>        # put it away: processes stopped, work saved, branch kept
scope task close <id|slug>          # archive it and forget it (--delete-branch)
scope task restore <id|slug>        # bring an archived task back, with the changes saved at archive
scope task rebase [<id|slug>]        # bring it up to date with main now: rebase when clean, ask its thread when not
scope task branch add [<id|slug>] <branch> # a second worktree of a repository, on that branch (--repo, --from, --pr)
scope task branch list|remove [<id|slug>] … # every worktree of the task; take one out, its changes saved, branch kept
scope task checkpoints [<id|slug>]   # its checkpoints: one snapshot of the sandboxes per turn that changed a file
scope task restore-checkpoint [<id|slug>] <n>
                                    # put checkpoint n's files back; the files as they are become a checkpoint first
scope task topic [<id|slug>] <topic> # file it under a topic later (--clear, --no-children)
scope task milestone add|done [<id|slug>] … # a mission's milestones (--validate, --child); see missions
scope schedule list|run [<name>]      # the scheduled prompts: next fire and last run; or fire one now
scope gc [--dry-run]                # run the automatic cleanup now; --dry-run also weighs the sandboxes
scope release [X.Y.Z]               # cut a release from a clone of main in Scope's home (--repo, --dry-run, --force)
scope config get|set <key> [value] # agents' budgets, applied live; your terminal only
scope summary [period]              # what was done over a period, scope by scope (--scope, --task)
scope usage [period]                # how Scope itself was used: controls, commands, what never is
scope mcp                           # speak MCP on stdio
scope ping                          # is Scope listening, and what may agents do

Every command takes --json. --scope accepts a slug, a name, an id or a path; omitted, it is the caller's own scope, then the scope holding the working directory, then the only scope there is. --sock and --home say which Scope to talk to — a Debug build listens on ~/.scope-debug/scope.sock.

$ scope thread new --scope acme --driver claude-code --model claude-fable-5-1 -p "why is CI red?"
thread 3f9a2c17be04 — acme [claude-code · claude-fable-5-1] in acme
/Users/me/work/acme

$ scope task new "fix the flaky login test" --repo api --dry-run
would create the task “Fix the flaky login test”
branch      fix/flaky-login-test
slug        fix-flaky-login-test
sandbox     ~/.scope/sandboxes/acme/fix-flaky-login-test
repo        api → ~/.scope/sandboxes/acme/fix-flaky-login-test/api (branch created)

scope list threads ends each row with what its agent did last, and when: the last tool it ran and on what — a file (relative to the thread's folder), the first line of a command, a search pattern, a URL — or how its turn ended. --json and the MCP tool carry it as activity; a thread whose driver reports nothing (a shell) has none. TOKENS is what a Claude Code thread consumed over the last five hours (tokens in JSON), read from its transcripts.

$ scope list threads
THREAD        TITLE  DRIVER       MODEL             STATE    SCOPE  TASK  TOKENS    BY    ACTIVITY
3f9a2c17be04  acme   claude-code  claude-fable-5-1  running  acme         1.2M · 5h  user  Edit Sources/Login/Session.swift · 2m ago
8a18d7476063  ci     claude-code                    done     acme         310k · 5h  user  finished · 1h ago

--model on thread new and task new (model in MCP) picks what the driver runs on, through the profile's modelArgs; the thread keeps it across relaunches and resumes, and the window subtitle shows it. Left out, an agent's thread inherits the agent's own model when it runs the same driver, else the scope's default (its settings sheet), else the driver's default (Settings ▸ Drivers), else the driver decides. A driver whose profile has no modelArgs — the shell — refuses one.

scope thread read prints the last 200 lines of a thread's terminal — scrollback included, up to 2000 with -n — between two markers, under a line saying the text is untrusted terminal output. Line numbers stay put as the scrollback grows: the last line tells you the --cursor that reads the page before. It is how an agent finds out what another thread said, without typing into it — its own child, or a thread in another task or scope. --reply prints only the agent's last answer, as Claude Code and Codex report it at the end of a turn: what it concluded, without the spinners and redraws of its terminal.

scope thread wait takes one thread id or more and returns once each has finished its turn, needs an answer or a permission, or exited — then prints every thread's state and last reply. --any returns at the first one, --timeout (600 s by default) answers anyway and names those still at work. A thread just handed a prompt counts as at work until its driver reports on it, so a wait right after thread send or task new does not return before the work starts. An answer that lands during the wait ends it, and a thread that still reads running although its last answer is newer than anything that started a turn counts as done. A Claude Code turn that ends with sub-agents still running in the background does not end the wait: the thread is still at work until they report and it answers. Shell commands and Monitors it left running in the background — a dev server, a watcher — never hold it: the answer lists them (id, state, command, exit code, output file, and any /loop wake-up or cron), as do scope list threads and scope thread read; read the output file rather than waiting. For a thread in a task, the answer carries the task's pull request as GitHub reports it (state, checks, mergeability, review), refreshed as the wait ends — the same line scope list tasks shows in its PR column — so no gh pr view is needed to know where the work stands. A shell reports no turns and never settles. scope thread send --wait (MCP wait: true) types the message, then waits for the answer the same way: one call instead of a send and a wait.

scope thread send from a thread is a message: it lands in the other terminal under a line naming its sender (thread id, title, task), so the receiving agent knows whom to answer and that the request is not yours. --no-enter sends keystrokes and carries no such line. A thread may not type into itself. scope thread new --task finds a task in any scope; --scope settles a slug two scopes share.

--command (command: true) is for the driver's own slash commands — /model claude-opus-5-5, /clear, /compact — which a sender line would turn into prose: the text is typed verbatim, with no line saying who sent it, and submitted. From your terminal it reaches any thread; an agent may command only the threads it opened and theirs, unless Settings ▸ Automation ▸ Driver commands opens every thread.

scope task new --issue 123 (issue over MCP) works on a GitHub issue: its title, body and labels open the brief, the task records it, and the context file asks for Closes #123 in the pull request. @task:<slug> and @thread:<id> in any prompt or message are replaced by that task's or thread's context — brief, branch, pull request, last answer kept — between markers; see Mentioning a past task.

scope task new --topic <text> files the task under a topic: tasks sharing one sit together in the sidebar, under one row. A task created from inside a task gets that task's topic unless another is named — and when that task has none, both are filed under its name — so what an agent splits off lands next to it. An orchestrator at the scope root has no task to inherit from: it names the topic of the tasks it fans out. scope list tasks shows each task's topic.

scope task new --attempts <n> runs the brief n ways: n sibling tasks under a topic named after the title, on <branch>-a1…-an, each with its own thread; --models a,b,c and --drivers x,y,z give each attempt its model or driver (one value for all, or one per attempt). The answer lists every attempt with its task, branch and thread; --dry-run lists what would be created. An agent's attempts all count against its task budget, and the refusal says how many would fit. Comparing and keeping one happens in the app: Compare attempts… in the topic's menu.

scope task topic <id|slug> <topic> files a task that already runs, and --clear takes it out of its topic; without a task, it is the caller's own. Only the label changes. The tasks it started, and theirs, follow while they still share its old topic — they got it from it, so they are the same piece of work — and --no-children moves it alone. The MCP tool is scope_task_topic.

scope summary last week lists, scope by scope, every task created, archived, closed or worked on in the period — finished or dropped alike — with an outcome (merged, delivered, abandoned, archived, active), its pull request, its topic, the opening of its brief, and how long its agents worked and how long it waited on you (a question, a permission, a result not yet followed by a prompt), then the threads opened outside tasks. The period reads today, yesterday, this week, last week (the previous calendar week, Monday to Sunday), last month, last 14 days, 2026-10-01..2026-10-14, since 2026-10-01; the default is the last seven days. --task <slug> prints one task's whole brief, and the last answers its threads gave before it was put away; each task's line carries the opening of that answer. Each task and thread carries the tokens its Claude Code threads consumed, all told. The installed /scope-summary skill has an agent turn it into an account.

What a task leaves behind

About half of the tasks are studies with no pull request: their deliverable is the agent's final answer, which used to go with the thread when the task was archived. Now archiving or closing a task keeps the last reply of each of its threads (its end, 64 KB), and the task's report file when it wrote one: https://github.com/maastrich/scopeRT.md in the task root or a sandbox, or the file named with scope task new --deliverable docs/study.md (deliverable in the MCP tool), 1 MB at most. They live in ~/.scope/tasks/deliverables/ and outlive a close. scope task show <slug> (scope_task_show) prints the brief and everything kept, for an open, archived or closed task; in the app, Read deliverable — in the Task section of a restored task, or from the palette for an archived one — opens it in the reading column.

It is built from records, not conversations: of what was said in a thread, Scope keeps only that last answer. Closing a task or a thread deletes its record, so a closed one now leaves a line in ~/.scope/history.jsonl; work closed before this version left nothing. A pull request's state is the last one Scope saw while its task was open.

scope usage last week reads the log Scope keeps of its own interface — on this Mac only, in ~/.scope/usage/, never sent anywhere: the controls, commands, sheets and inspector sections used most, per area; those never used in the period; for each command, how often it came from its shortcut, the menu, the palette or a click; the CLI and MCP calls made by you and by agents; the time spent in each sheet and section; and what rose or fell against the period before. Time on screen counts only while Scope is frontmost, one of its windows is visible, the session is unlocked and you touched the keyboard or the mouse in the last two minutes; the report says since when it is measured that way, and ignores the durations logged before. It holds ids, never what you type, a path or a name. Settings ▸ General ▸ Usage turns it off or clears it. The MCP tool is scope_usage.

Scheduled prompts

Scope can send a prompt on its own — every hour at a minute, every day, on weekdays or once a week at a time — to a scope's orchestrator, or into a new task with a driver and model of its own. Schedules live on the scope (Settings ▸ Automation ▸ Schedules, or the scope's settings sheet): name, rule, prompt, target, paused or not, and the last run. Two examples are offered at creation, paused: a morning look at the pull requests whose checks are red, an evening scope summary today. Occurrences come from the calendar, so a daily 09:00 stays 09:00 across the clock change; at launch a daily, weekday or weekly prompt missed in the last day fires once (Catch up at launch, on by default). The reply lands in the Inbox as Schedule <name> ran — <first line>, with Read reply. scope schedule list (scope_schedule_list) shows every schedule with its next fire and last run; scope schedule run <name> (scope_schedule_run) fires one now, paused or not — from an agent, with the approval set for creating a task.

Exit codes: 0, 64 for a usage error, 77 when Scope refused, 1 for anything else.

Links

A scope:// link asks for a task — from a README, an issue template, a bookmark:

scope://task/new?scope=acme&repo=api&prompt=Fix%20the%20flaky%20login%20test

It takes prompt (required), scope (default: the scope in the sidebar), repo (repeatable), branch, title, slug, driver, and setup=0 to skip the setup commands. Scope shows what the link asks for and creates nothing until you confirm — a link can come from any web page — then takes the same path as scope task new. A Debug build answers scope-debug:// instead.

The MCP server

scope mcp speaks MCP on stdio with the same commands as tools — scope_list, scope_thread_new, scope_thread_send, scope_thread_read, scope_thread_wait, scope_thread_stop, scope_thread_close, scope_task_new, scope_task_archive, scope_task_close, scope_task_restore, scope_task_rebase, scope_task_branch_add, scope_task_branch_list, scope_task_branch_remove, scope_task_checkpoints, scope_task_restore_checkpoint, scope_gc, scope_release, scope_ping. Arguments are snake_case, and the spellings an agent guesses from the command line are understood as meant — dryRun, no_thread for open_thread: false, message for text, a single repo. Anything else is refused rather than ignored, with the list of what the tool takes. They are the same commands: the server holds no logic of its own, so the terminal and the agent can never drift apart.

Settings ▸ Automation ▸ MCP server registers it with Claude Code, Codex and Cursor for your user, so every session you start — in Scope or in any other terminal — has it: Claude Code through its own claude mcp add --scope user, Codex in ~/.codex/config.toml, Cursor in ~/.cursor/mcp.json, touching only the scope entry. The command is the helper inside the app bundle, so an update keeps it working. By hand, the same thing:

{"mcpServers": {"scope": {"command": "/Applications/Scope.app/Contents/Helpers/scope", "args": ["mcp"]}}}

scope_task_new is marked destructive. With dry_run the answer is the title, branch, sandbox and worktrees it would create (and, with attempts, every attempt), with nothing written; the description keeps it for when the agent cannot tell which repositories the work needs, so a task the agent can describe costs one call.

The Scope skill

Settings ▸ Automation ▸ Skills installs a scope skill for your user — one SKILL.md under ~/.claude/skills, ~/.codex/skills or ~/.cursor/skills — so every session of those agents knows when to put work in a task, how to refer to one by name or slug, how to brief a thread so it finishes alone, wait for it and read its answer, and close the task — with both spellings of every command, since a session Scope did not launch has the MCP tools and no scope on its PATH. When an update changes the text, Scope rewrites the copies it installed at its next launch, and only those — a copy under the skill's former name, scope-tasks, moves to the new one; a folder of the same name that Scope did not write is never touched. A task's name and slug are one right-click away in the sidebar (Copy Task Name, Copy Task Slug) and a click on the copy button next to the name in the inspector.

What an agent is allowed to do

The scope command line in your own terminal is you, and is never filtered. A request from inside a thread — or through scope mcp from anywhere, since a globally registered server is reached from sessions Scope never launched — is an agent, and goes through Settings ▸ Automation:

SettingDefaultWhat it does
Let agents drive ScopeonOff refuses every write from a thread.
Open tasks12How many tasks agents may keep open at once, every scope together. Archived tasks and yours do not count.
Running threads24How many threads agents may keep running at once, every scope together. Stopped threads and yours do not count.
Depthno limitA thread you opened is at depth 0; what an agent opens from it is one deeper. Set a limit to fence agents to a few generations; 0 keeps them from opening anything.
Talking to threadsany threadWhich threads an agent may read, type into, stop or close: any, in every task and scope, or only the ones it opened.
Driver commandsonly the ones it openedWhich threads an agent may hand a driver command to (thread send --command: /model, /clear…), typed verbatim with no sender line. Never wider than Talking to threads.
Opening a threadwithout askingAlso available: after asking, never.
Creating a taskwithout askingA task writes a branch and a worktree per repository, all of it undone by closing the task. Set it to after asking to confirm each one.
Releasesafter askingscope release from an agent. The one place the autonomy default flips: a tag pushed is a version shipped, and nothing takes it back. A dry run never asks.

Threads talk to each other: by default an agent may read and type into any thread Scope runs — another task's, another scope's, yours — and every message it sends is signed with its thread id, so the receiver knows who is asking and can answer back. Only its own terminal is off limits. Only the ones it opened is the fence for whoever wants each agent confined to the threads it started; an agent outside Scope is then confined to the threads agents outside Scope opened. Closing a task — worktrees removed, branch deleted when asked — follows the same approval as creating one.

Any task may create tasks: an orchestrator splits a change across tasks, and a task splits its own work further. What stops a loop of agents starting agents is not how deep the chain goes but how much it holds: each task is a worktree per repository, each thread a process. So the budgets count what agents keep open right now, across every scope, and refuse the request that would go past them — with the way out in the answer: archive the tasks that are done, close the threads that are. Requests still being carried out hold their share, so five sent at once cannot all take the last slot. A depth limit remains for whoever wants one. config.json is read at launch and rewritten by the app, so raise a budget from a terminal with scope config set automation.maxAgentTasks 20 (or automation.maxAgentThreads; scope config get lists them): it takes effect at once, as the Settings window would. Agents are refused it — from a thread or through scope mcp — and it is not an MCP tool. With approvals set to after asking, Scope shows one question at a time; a question left past the approval timeout is refused, and so is a request that finds three already waiting.

Every thread records who opened it, the line of threads above it and its depth, so the chain survives a restart — scope list threads shows it. Only the ones it opened reaches everything an agent set in motion: the threads it opened, the ones those opened, and so on down. A SCOPE_THREAD that names no thread the app is running is refused outright.

The socket is your account. ~/.scope/scope.sock is a unix socket with mode 0600, so only your user can connect — but everything running as you can: any program, any script, any agent in any terminal. The automation settings shape what a request from a Scope thread may do; they are not a defence against software you chose to run. It is the posture the driver hooks have always had, now with answers coming back.

The protocol

One exchange per connection. The client writes a frame, the app answers with newline-separated JSON lines and closes; the last line is always the result. The header is what tells a control request apart from a hook message.

→ scope-rpc/1
→ {"caller":{"client":"scope-cli/0.4.0"},"id":"7f2a","method":"thread.new","params":{"scope":"acme"},"rpc":1}
← {"id":"7f2a","kind":"pending","message":"waiting for you to approve: …","rpc":1}
← {"id":"7f2a","kind":"result","ok":true,"result":{"thread":"3f9a2c17be04",…},"rpc":1}

Methods: ping, list, thread.new, task.new. An unknown method or a newer rpc answers unsupported rather than failing to parse, so a scope binary that outlives its app says so instead of hanging. Error codes: bad_request, unsupported, denied, not_found, failed, timeout.
