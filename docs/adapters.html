Hooks and thread states

Scope does not parse terminal output to guess what an agent is doing. The agent tells it, through its own hook mechanism, over a unix socket.

The pipeline

agent hook  →  scope-hook (stdin: JSON)  →  $SCOPE_SOCK  →  adapter  →  thread state

scope-hook is a tiny helper shipped inside the app bundle (Scope.app/Contents/Helpers/scope-hook). It reads the hook payload on stdin, adds SCOPE_THREAD and writes one line to the socket named by SCOPE_SOCK. It never blocks the agent: if Scope is not listening, it exits quietly.

Claude Code

For a driver with "adapter": { "kind": "claude-hooks" }, Scope writes a settings file per thread and starts the CLI with --settings. The events it subscribes to:

HookBecomes
SessionStartno change; the session id is captured, which is what lets Relaunch pick the session back up
UserPromptSubmit, PostToolUserunning — after a Stop, only a new prompt starts the next turn: a background command or sub-agent still reporting, or a hook delivered late, leaves the thread done
PreToolUse on AskUserQuestion / ExitPlanModewaiting — question
Notificationwaiting — permission once a permission dialog has sat unanswered for about six seconds (an elicitation dialog is a question) — and a macOS notification when Scope is in the background. A permission that auto mode, bypassPermissions or another PermissionRequest hook grants never shows as waiting
Stop, SessionEnddone
SubagentStart, SubagentStopno change; the sub-agents still running are counted, and scope thread wait holds while one of them runs in the background after a Stop
StopFailurefailed, with the reason (rate limit, billing, overloaded)

Two moments have no hook at all, and come from what you type into the thread instead: Esc or Ctrl-C during a turn ends it (idle), and Return on a permission prompt resumes it (running). Claude Code's idle_prompt notification, sent a minute after any answer you have not replied to, is deliberately ignored: the turn is already done, nobody is asking anything.

Scope also keeps what the hooks say about the work itself: the tool each PostToolUse reports and what it was about, when each turn started and how it ended, the last answer, and where Claude Code writes the session's transcript. It lives beside the thread's record, in ~/.scope/threads/<id>.activity.json, survives a restart, and goes when the thread is closed.

Your plan's limits

A Claude subscription (Pro, Max) is not a budget of tokens: it is a rolling five-hour window and a weekly one, sometimes a weekly one per model, each a percentage that resets. That is what the toolbar meter leads with — the window nearest its ceiling, as 31% · 35 min, coloured as it tightens — and its popover lists every window with its percentage and when it resets, the tokens under them.

The figures are Claude Code's own. The JSON Claude Code hands its status line on every answer carries rate_limits: one object per window with used_percentage and resets_at, for claude.ai subscribers only, after the session's first answer. The per-thread settings file Scope passes on the command line sets the status line to scope-hook statusline, which forwards that object to the app and then runs the status line your own settings name — the project's, then ~/.claude/settings.json, in Claude Code's order — on the same input, printing what it prints. So the bottom of the terminal keeps showing what it showed, and nothing in ~/.claude is modified. The plan's name comes from the account Claude Code keeps in ~/.claude.json, read only.

Scope never guesses a percentage. Until a thread has answered, or on an API key where Claude Code reports no limits, the meter says the limits are unknown and shows tokens as before. The last report is kept in ~/.scope/limits.json so it shows at launch, with its age; after thirty minutes without a newer one it is marked stale, since usage from claude.ai or another machine would not be in it. scope ping and scope list carry the same windows (limits, with each window's level and seconds to its reset), as do the scope_ping and scope_list MCP tools, so an agent near a ceiling can slow down rather than open more threads. Turning the meter off in Settings also stops installing the relay; a thread opened while it was off needs a relaunch to report.

Tokens consumed

Every 30 seconds Scope reads what each Claude Code thread's transcript gained since the last look — only the bytes appended, off the main thread — and sums the usage of each model call: input, output, cache writes and cache reads, with the model and the time. A response is written as several lines carrying the same message id; it counts once. The transcripts of the subagents a session runs (the Task tool) count towards its thread, since they spend the same quota. The transcripts are only read, never written.

The toolbar meter shows the last five hours across every scope; its popover adds today, the last seven days, each scope and the threads that spent most, with what the five hours are made of. A task's total sits beside its name in the inspector band and in its hover card. The figures include cache reads, which are most of any total. The tokens say who spent the limits above; where Claude Code reports no limits they are the meter's main figure, consumption rather than what is left — unless you type a budget of your own per five hours (Settings ▸ General ▸ Usage), which turns it into a gauge. The same pane can add what the tokens would have cost at API list prices, labelled as such; it is off by default, since a subscription is not billed per token.

The counts live in ~/.scope/tokens.json, with where each transcript was read up to: the minute-by-minute detail for eight days, each thread's total for 90 days after its last call, closed threads included. Other drivers report no tokens.

Your own ~/.claude/settings.json is not modified: the per-thread file lives under ~/.scope/threads/ and is passed on the command line.

What the dot says

DotMeaning
green, breathingrunning: the agent says it is working
squarewaiting for you — a question or a permission; counted in the badge until you answer or Mark as Read
diamondfailed: the turn stopped on an API error
bluedone: finished while you were not looking; showing the thread clears it
greyidle: seen, ready for the next prompt
ringexited: the process is gone

The toolbar pill and the row's tooltip say which it is in words — Needs your answer, Needs permission, Failed: rate limit. A task row's glyph tells a question from a permission too, and a collapsed group shows the most urgent dot of its threads: waiting, then failed, running, done, idle.

Codex and Cursor

Codex is wired through its notify configuration, with the same helper and the same socket. notify only reports the end of a turn, so a prompt you type into a Codex thread is what marks it running. Cursor's profile declares its hooks adapter, but it is not wired yet: like a shell, a Cursor thread only knows it is alive. A tool without an adapter still runs perfectly — its row simply shows no live state.

Notifications and the badge

When a thread starts waiting while Scope is not frontmost, you get a macOS notification with Reply, Go to thread and See delta actions. The Dock badge counts the waiting threads, and the optional menu bar item shows the Inbox, so you can leave the window behind and answer from there when an agent needs you.

The notification quotes the agent: the question it asks (Claude Code's AskUserQuestion, the plan of ExitPlanMode, a dialog's message), else the end of the answer it just gave; for a finished turn, the start of its answer. Markdown is stripped and the quote cut to about 180 characters, so you can tell from the banner whether it is worth opening. A failed turn still says its error. Reply types your answer into the thread and presses ↩, exactly as scope thread send does, without bringing Scope up; the notification goes once it is sent. Settings › General › Notifications › Show what the agent said (on by default) turns the quote off, for when your screen is shared.

The assistant

On events only — a turn that ends, a thread running for more than four minutes, a task being created — Scope can hand the end of the terminal to a small model and get labels back: what the agent is doing, whether it seems stuck and why, whether a finished turn is worth a notification, whether a task without a pull request looks done, which of the scope's topics a new task belongs with. It never acts on any of it, and it never reads the same words twice: a thread whose terminal has not moved keeps its last digest (asked again every eight minutes at most), a finished turn is triaged only when a notification could be quieted by it, and the same answer reported twice gets one verdict and one notification.

The first model is Apple's on-device one (macOS 26, Apple Intelligence on): free, local, about a second per answer, good at exactly this kind of structured classification. Settings › Assist › On-device + Haiku adds Claude Code's light model as a second opinion on a stuck verdict, and as the fallback when the on-device model is unavailable — through claude -p with no tools at all, since what it reads is untrusted terminal output, under a daily cap you set (40 by default). Each call counts against your subscription like any other.

What you see: the activity line under a running thread takes the model's words; a thread read as stuck says Seems stuck — reason in the sidebar, in the Inbox and as a notification, with a Not stuck answer that is remembered as a false positive; a finished turn the model reads as informational stays silent (a question or a failure always notifies), and one it reads as blocking notifies with a Not Blocking action that is remembered the same way; a task whose last reply reads as a deliverable shows Looks finished — archive? in its band, a proposal with its own ✕; a task created without a topic is filed under one of the scope's topics when one fits. Every decision goes to the usage log by its id and tier only.

The socket

$SCOPE_SOCK points at ~/.scope/scope.sock — or, when SCOPE_HOME is too deep for a unix socket path, at $TMPDIR/scope-<uid>-<hash of the home>.sock. One JSON object per line:

{"thread":"3f9a2c17be04","kind":"Notification","session_id":"…","payload":{…}}

Anything that can write a line to a unix socket can drive the state of a thread — a wrapper script, a CI watcher, your own tool. scope-hook is only the convenient way to do it.
