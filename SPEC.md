# Scope — Spec v0.2

> App macOS native, open-source. Une salle de contrôle pour agents de code en ligne de commande : tu déclares un dossier comme *scope*, tu y lances des *threads* (Claude Code, Codex, Cursor, n'importe quel *driver*), chaque *task* travaille dans une *sandbox* isolée, la *base* reste intacte, et tu vois le *delta* de n'importe quel repo à tout moment.
>
> **Focus Claude Code.** Scope se concentre sur Claude Code : c'est le driver pour lequel il est construit, et il en montre et en pilote tout ce qu'il expose (sous-agents, tâches de fond, demandes en attente, serveurs MCP, compactions…) pour qu'on suive chaque agent sans lire son terminal. Les autres drivers (Codex, Cursor, shell) continuent de marcher tels quels, sans ces features ; on ne cherche plus la parité avec eux.

Convention d'écriture : **Scope** (majuscule) désigne l'app, *scope* (minuscule) désigne un dossier déclaré.

---

## 1. Vision et principes

**Problème.** Travailler avec des agents de code sur plusieurs repos aujourd'hui, c'est N terminaux ouverts à la main, des `git worktree` tapés de tête, une `main` qui finit salie par une session, et aucun endroit où voir *ce qui a changé, où, par quel agent*.

**Scope** s'instancie sur n'importe quel dossier, lance des agents dans des terminaux embarqués, isole chaque task dans des worktrees, et montre en permanence la carte des repos, les diffs et l'état de la branche stable.

**Principes**

1. **Claude Code d'abord.** Le terminal lance un binaire, et Claude Code, Codex, Cursor ou un shell nu restent des profils. Mais une feature n'a plus besoin d'exister pour tous les drivers pour être livrée : ce que Claude Code expose (hooks, transcript, status line) est lu à fond, et ce qui en sort n'apparaît que sur ses threads. Les autres drivers gardent ce qu'ils ont, sans promesse de parité. Inventaire des sources : `docs/research/claude-native.md`.
2. **Aucune structure imposée.** Un scope est n'importe quel dossier : une org GitHub clonée, un dossier de projets, un seul repo. Scope n'écrit rien dedans par défaut.
3. **La base est intouchable.** Aucun agent n'écrit dans le checkout principal. Les tasks vivent dans des sandboxes. Une seule exception, voulue par l'utilisateur et réversible par construction : *Try in my checkout* (§4.5), désactivée par défaut, refusée aux agents quoi qu'il arrive — la base est stashée et détachée sur la branche d'une task, puis remise exactement où elle était.
4. **Git est l'API.** Deltas, branches, worktrees : Scope orchestre `git`, ne le remplace pas.
5. **Le terminal est l'interface de l'agent.** Pas de chat UI, pas de wrapper. Scope ajoute du contexte autour, pas au milieu.
6. **Natif, rapide, lisible.** SwiftUI/AppKit, zéro Electron, zéro serveur, un code qu'un contributeur peut lire en une soirée.

## 2. Lexique et modèle de domaine

| Terme | Définition | Exemple |
|---|---|---|
| **Scope** | Un dossier déclaré par l'utilisateur. Contient 1..n repos git, ou est lui-même un repo | `~/contributions/acme/`, `~/dev/mon-projet/` |
| **Repo** | Un dépôt git découvert dans un scope (profondeur 1 par défaut, réglable) | `acme/api`, `acme/web` |
| **Base** | Le checkout principal d'un repo, sur sa branche par défaut. Lecture, vérification, shell perso. Jamais touché par un agent | `~/contributions/acme/api/` sur `main` |
| **Graph** | Cache structuré décrivant chaque repo du scope : rôle, stack, points d'entrée, relations, commandes de setup et de test | `~/.scope/graph/acme.json` |
| **Driver** | Profil déclaratif d'un agent CLI : commande, args, env, fichier de contexte, adaptateur | `claude`, `codex`, `cursor-agent`, `zsh` |
| **Thread** | Un driver qui tourne dans un PTY, attaché à un scope et optionnellement à une task. Long, interruptible, reprenable | "Codex · acme · auth-refresh" |
| **Task** | Unité de travail nommée, sur 1..n repos d'un scope. Chaque repo impliqué reçoit une sandbox | `auth-refresh` → sandboxes sur `api` et `web` |
| **Sandbox** | `git worktree` d'un repo sur la branche de la task. Isole le *code*, pas le process : l'agent garde son accès disque et réseau | `~/.scope/sandboxes/acme/auth-refresh/api/` |
| **Delta** | Le diff, agrégé sur les repos d'une task ou vu repo par repo | — |

**Relations.** Un scope a des repos, des tasks et des threads. Une task a une sandbox par repo impliqué et 0..n threads. Un thread a un driver et un cwd (la task, ou la racine du scope). Deux scopes peuvent se chevaucher (un repo d'une org déclaré aussi comme scope seul) : c'est autorisé, Scope ne juge pas la structure.

**Kinds de scope**, détectés automatiquement :

- *Repo scope* : le dossier est un repo git. Les tasks portent sur ce seul repo.
- *Multi-repo scope* : le dossier contient des repos. Les tasks choisissent leurs repos.
- Un repo qui contient des repos imbriqués (submodules, vendoring) est un repo scope avec repos secondaires listés dans le graph.

## 3. Arborescence sur disque

Scope ne touche pas au dossier de l'utilisateur. Tout ce qu'il produit vit dans un dossier home, court et sans espace pour rester agréable dans un terminal.

```
~/.scope/                              # SCOPE_HOME, surchargeable
  config.json                          # scopes déclarés, préférences, éditeur
  drivers/*.json                       # profils de driver (les built-in sont copiés ici, éditables)
  graph/<scope-slug>.json              # graph par scope (cache)
  sandboxes/<scope-slug>/<task-slug>/  # racine de task = cwd du thread (multi-repo)
    AGENTS.md                          # projection du graph + périmètre de la task
    <task-slug>.code-workspace         # multi-root pour Cursor / VS Code
    api/                               # sandbox = worktree, branche feat/auth-refresh
    web/
  threads/<thread-id>.json             # driver, cwd, id de reprise, logs
  usage/usage-YYYY-MM.jsonl            # journal local d'usage de l'app (ids seulement, 180 jours)
  usage/registry.json                  # tout élément instrumenté : id, libellé, zone
  tokens.json                          # tokens consommés par thread, lus des transcripts Claude Code
  limits.json                          # limites de l'abonnement, telles que Claude Code les a rapportées en dernier
  scope.sock                           # socket unix pour les adaptateurs

~/Library/Application Support/Scope/   # état purement UI (fenêtres, splits, onglets)
```

Option par scope : *sandboxes à côté des repos* (`<scope>/.scope/sandboxes/`), pour ceux qui préfèrent des chemins relatifs courts. Désactivée par défaut.

**Le disque fait foi.** `config.json`, `tasks/<id>.json` et `threads/<id>.json` sont surveillés (FSEvents sur les deux dossiers, source vnode sur le fichier et son dossier pour la config, pas de surveillance récursive du home) : un fichier modifié hors de l'app — un topic renommé dans un éditeur, un champ corrigé, un enregistrement retiré — est rechargé sans redémarrage, et la sidebar, l'inspecteur, la CLI et le MCP le reflètent. Pas de boucle : chaque store garde l'empreinte SHA-256 des octets qu'il a lus ou écrits en dernier (`RecordLedger`) ; un événement dont les octets sont connus est une écriture de l'app et est ignoré avant tout décodage ; un rechargement n'écrit jamais rien (pas de normalisation, pas d'allocation de port, pas de quarantaine), et l'écriture ultérieure d'un record rechargé est notée avant d'être faite, donc ignorée à son tour. Les rafales font un seul réveil (300 ms de silence). Un fichier qui ne décode pas (écriture partielle, faute de frappe) ou qu'un Scope plus récent a écrit est laissé tel quel, l'état en mémoire gardé, le fichier relu à son prochain changement. Règle de conflit : le disque gagne, sauf une sauvegarde de config encore en attente (150 ms), qui écrase une édition faite dans cette fenêtre, et une task en cours d'archivage, qui réécrit son record à chaque étape ; toute autre modification de l'app est sur le disque avant d'être en mémoire, une `mutate` en vol se réapplique sur ce qui est arrivé. Un thread en cours garde ce que son processus sait mieux que le fichier (état, sorties, lancements, id de reprise) et prend le reste (titre, task, rôle, opt-out de relance) ; son fichier retiré sous lui est réécrit à son prochain changement. Un record de task retiré à la main est une task oubliée, pas clôturée : ses dossiers restent pour `scope gc`. Testé dans `StateReloadTests`.

## 4. Fonctionnalités

### 4.1 Scopes

- **Déclarer un scope** : `⌘O`, ou depuis le Finder (extension "Ouvrir dans Scope"). Pas de glisser-déposer : un drop dans la fenêtre va au terminal, qui insère le chemin sur la ligne de commande. Aucune racine, aucune hiérarchie : la sidebar liste les scopes déclarés, dans l'ordre choisi.
- **Découverte** : Scope repère les repos (dossiers contenant `.git`) à profondeur 1, réglable par scope. Le remote `origin` sert à afficher `owner/repo` et à détecter les orgs.
- **Watcher** FSEvents sur chaque scope + rafraîchissement manuel.
- **Repos distants non clonés** : si le scope correspond à une org GitHub et que `gh` est présent, `gh repo list <org>` alimente le graph avec des repos grisés et un bouton *Cloner*.
- Retirer un scope ne supprime rien sur le disque, sauf demande explicite pour ses sandboxes.

### 4.2 Threads

- **Créer** : choisir un driver (sinon celui de *Réglages ▸ Default driver*, voir §5 *Driver*) et un cwd. Par défaut, une task (l'agent voit uniquement ses sandboxes). Sinon la racine du scope (l'agent voit les bases : à utiliser pour explorer, pas pour modifier).
- **Terminal embarqué** : PTY complet (SwiftTerm), 256 couleurs, resize, copier/coller, scrollback, recherche. Onglets par thread, splits horizontaux et verticaux.
- **Environnement injecté** : `SCOPE_THREAD`, `SCOPE_SCOPE`, `SCOPE_TASK`, `SCOPE_SOCK`, `SCOPE_HOME`, plus l'env du profil de driver.
- **États** : `idle` · `running` · `waiting` (attend une réponse ou une permission ; une permission de Claude Code ne compte qu'une fois sa boîte de dialogue restée ~6 s sans réponse — celles qu'accordent le classifieur du mode auto, `bypassPermissions` ou un autre hook `PermissionRequest` ne passent jamais par `waiting`) · `done` (tour fini, pas encore vu) · `failed` (tour arrêté sur une erreur de l'API) · `exited`. Montrer le thread ramène `done` et `failed` à `idle`. Sans adaptateur, seuls `running` et `exited` sont connus.
- **Reprise** : au redémarrage, les threads qui tournaient quand l'app s'est arrêtée (quit, mise à jour, crash, reboot) repartent seuls, en reprenant la session du driver quand elle est connue (commande de reprise du profil, ex. `claude --resume <id>`), sinon dans le même cwd. Le thread sélectionné part en premier, les autres sont échelonnés. Un thread dont le scope, la task ou le cwd a disparu reste arrêté et dit pourquoi. Réglage pour désactiver, opt-out par thread, ⇧ maintenu au lancement pour sauter une fois. Tout thread arrêté propose *Relancer* (qui reprend quand il peut) ou *Nouvelle session*. Un agent dont le tour était en cours au moment de l'arrêt (`turn.started` sans fin, processus vivant) est marqué sur son enregistrement (`interruptedTurn`, à la fermeture ou à la lecture d'un enregistrement resté `running`, cas du crash) ; une fois relancé et son prompt revenu (`session.started` de ses hooks, ou le bracketed paste actif depuis 2 s ; 30 s au plus, sans jamais taper à l'aveugle), Scope lui envoie, signé, un message lui demandant de reprendre là où en est le worktree (`git status` / `git log`, relire son plan, finir). Une seule fois par interruption ; jamais pour un shell ; abandonné si l'utilisateur tape avant. Réglage *Ask agents to continue after a restart* (actif par défaut), ⇧ au lancement le saute aussi. La légende de la barre latérale et `scope list` disent « resuming after restart » pendant l'attente.
- **Fermer sans regret** : aucune commande destructrice sous le curseur dans la sidebar. Les contrôles qui apparaissent au survol d'une ligne sont *Ouvrir dans l'éditeur* (task) et un menu « … » ; *Fermer le thread*, *Archiver* et *Clôturer* sont dans ce menu, dans le menu contextuel, dans la barre de menus (`⌘W`, Thread ▸ Task) et dans la palette — jamais sur un bouton nu qu'un clic qui visait la ligne atteint. **Confirmation proportionnée** (`confirmCloseRunningThread`, un seul réglage pour les threads et les tasks) : on ne demande que s'il y a quelque chose à perdre (`CloseGuard` : un agent en plein tour, un shell dont le processus tourne, des changements non commités, une PR ouverte) ; un thread au repos, une task finie et mergée partent en un clic. La feuille a *Annuler* en bouton par défaut : un `↩` tapé pour le terminal ne confirme rien, le bouton destructeur se clique. **Annuler** : tout thread fermé et toute task archivée — par l'UI ou par un agent (`scope thread close`, `scope_task_archive`) — restent récupérables 5 min (`AppModel+Undo`) : un toast « “Titre” closed — Reopen » / « “Nom” archived — Undo » 10 s (le survol le retient, le nommant quand c'est un agent), Édition ▸ *Undo Close/Archive* et la palette pendant les 5 min ; les raccourcis `⌘Z` et `⇧⌘T` (dernier thread) seulement 30 s après une action **de l'utilisateur** — jamais pour celle d'un agent, sinon un `⌘Z` tapé dans un champ restaurerait une task qu'un agent vient d'archiver ; le reste du temps les touches restent à l'undo des champs et à *New Task*. Les threads raccrochés par l'archive ou la clôture de leur task (ou le retrait d'une branche, d'un scope) reviennent avec la task, pas seuls. Un thread rouvert reprend sa session de driver quand le profil sait (`resume`), sinon repart dans le même cwd ; une task revient avec ses sandboxes et ses changements (*Restaurer*). Une task clôturée (record supprimé) n'a pas d'annulation : c'est pourquoi elle est derrière la même question. Les annulations sont comptées dans le journal d'usage (`undo.reopen-thread`, `undo.restore-task`, contexte `toast` / `shortcut`). **Gestes** : aucun geste de ligne n'archive ni ne ferme — le pan vertical défile, le swipe horizontal change de scope (`PageSwipe`, axe verrouillé, seuil de distance et de vitesse, retour visuel, rien en deçà), le tap à deux doigts ouvre le menu contextuel ; un geste ne doit jamais devenir une action destructrice sans seuil et sans Undo.
- **Threads résidents** : chaque scope déclaré garde à sa racine un *orchestrateur* (un agent — préférence *Orchestrator driver*, automatique = driver par défaut puis premier agent installé) et un *terminal* (le shell). Ce sont des threads ordinaires marqués d'un rôle (`ThreadRecord.resident`), créés par Scope — à la déclaration, au lancement, et rétroactivement pour les scopes existants. On ne peut pas les fermer (⌘W, bouton, menu, `thread close` refusent) ; ils partent avec leur scope. *Stop* reste permis et les laisse arrêtés jusqu'à *Relancer* ou jusqu'au prochain lancement de Scope (⇧ au lancement pour prolonger). Un processus qui meurt seul est relancé (crash → reprise de session, sortie propre → nouvelle session) avec un délai croissant ; trois sorties rapides d'affilée (< 10 s) ou un exit 127 et Scope abandonne en le signalant. Ils démarrent à la première visite du scope (ceux du scope ouvert au lancement), pas tous au démarrage ; un message envoyé à l'un le démarre. ⇧ au lancement les laisse arrêtés. Dossier du scope absent : arrêtés, repartent à la visite suivante une fois le dossier revenu. Dans la sidebar ils sont en tête (⌘1, ⌘2), hors *Loose threads*, et ne changent pas de groupe en mode *By state*.
- **Plusieurs drivers côte à côte** sur le même scope, y compris sur la même task.

### 4.3 Tasks et sandboxes

- **Créer une task** : nom → slug, choix des repos (pour un multi-repo scope ; suggestion depuis le graph : "quels repos pour *ajouter un refresh token* ?"), branche proposée d'après la convention du repo (le driver en headless lit les branches et les commits récents ; à défaut, préfixe dominant ou `feat/`/`fix/`, sinon le slug nu), depuis la base à jour (`fetch` puis branche depuis `origin/<default>`). Le préfixe `scope/` est réservé à Scope et refusé, avec la marche à suivre : omettre la branche, ou un autre préfixe comme `feat/`. La préférence `branchPrefix` n'est plus lue.
- **Partir d'une pull request** : sa tête est checkoutée au lieu d'une nouvelle branche. Explicite (`scope task new --pr <ref>`, `start_pr` côté MCP), elle doit se résoudre, sinon la création échoue. Sinon, seule une PR que le prompt demande de travailler compte — le prompt n’est guère que la référence ou s’ouvre sur une ligne qui l’est, ou une phrase s'ouvre sur un verbe d'action qui la vise (« review #123 », « rebase la pr <url> ») ; une PR citée pour contexte dans un brief n'est pas un point de départ. Une PR ainsi lue qui ne se résout pas dans le scope (autre repo, inexistante) est ignorée : la task part d'une nouvelle branche et la réponse le dit en une ligne.
- Pour chaque repo : `git -C <repo> worktree add <task-root>/<repo> -b <branche> origin/<default>`, puis préparation de la sandbox, en arrière-plan, avant que le premier thread ne démarre (il attend) :
  1. **Copie des fichiers non versionnés** de la base vers la sandbox, par globs (`.env*` par défaut ; jokers dans le nom de fichier seulement). Refus de `..`, des chemins absolus, d'une source symlink qui sort de la base et d'une destination dont le chemin passe par un symlink ; un fichier déjà présent n'est jamais écrasé ; un fichier copié que le repo n'ignore pas est ajouté à `.git/info/exclude`. S'y ajoutent, sans réglage, les entrées de `.claude/skills`, `.claude/commands` et `.claude/agents` que la base a et pas la sandbox (un `.claude/` ignoré) : chaque skill, commande ou agent copié en entier, mêmes refus, plus celui d'un dossier contenant un lien qui mènerait encore à la base. Copiés et non liés, pour qu'un agent qui modifie un skill modifie la copie de la sandbox ; jamais `settings.local.json` (permissions et environnement de l'utilisateur), que `copyFiles` peut toujours nommer. Claude Code retrouve seul le `.claude/` du checkout principal depuis un worktree où il démarre, mais pas depuis un worktree reçu par `--add-dir`.
  2. **Commande de setup** du repo (`pnpm i`, `bundle`, `make deps`) : le champ `setup` de la carte du graph, surchargé par repo dans la config du scope (`repoCommands` dans `config.json` : `setup`, `teardown`, `copyFiles` ; une chaîne vide désactive). Lancée avec `<shell> -c` dans la sandbox, avec l'environnement du shell de login plus `SCOPE_TASK`, `SCOPE_SCOPE`, `SCOPE_SANDBOX` (le worktree), `SCOPE_BASE_PATH` (le checkout principal), `SCOPE_DEFAULT_BRANCH` et `SCOPE_PORT`.
  - L'état du setup (`notRun` · `running` · `succeeded` · `failed` · `skipped`) et son log (borné à 64 Ko, la fin gardée) vivent sur le record de la task. Un échec va dans le Problem Center avec le log et *Relancer le setup*. Un setup interrompu par un quit est `failed` au lancement suivant.
  - Case *Lancer le setup* dans la feuille New Task ; `scope task new --no-setup`, `run_setup` côté MCP. Décochée, les fichiers sont copiés quand même.
- **Ports** : chaque task reçoit un bloc de 10 ports (41000–48999), stocké sur son record (stable au redémarrage), jamais partagé par deux tasks vivantes ; le premier est `SCOPE_PORT`, pour le setup comme pour les threads de la task.
- **Les serveurs d'une task** : tant qu'un thread de la task est vivant, toutes les 20 s, les process sous sa racine (la même recherche que le sweep) sont interrogés sur leurs sockets TCP en écoute (`proc_pidfdinfo`, l'équivalent de `lsof -iTCP -sTCP:LISTEN`) ; les ports du bloc de la task deviennent des puces `localhost:41003 ↗` dans la section Task et la carte de survol, un clic les ouvre dans le pane Browser de la task (`⌥`-clic : le navigateur système). Filtrage pur et testé (`ListeningPorts`, `PortBlock`).
- **Le poids disque des sandboxes** : la racine de chaque task ouverte est parcourue hors du main actor (taille allouée des fichiers réguliers, liens durs comptés une fois, liens symboliques ignorés — `SandboxSize`), après chaque setup et restauration et toutes les 10 min ; le chiffre est montré dans la section Task et la carte de survol, la feuille de réglages du scope donne le total des tasks ouvertes et les trois plus lourdes, `scope gc --dry-run` imprime les mêmes chiffres.
- **Une task depuis une issue GitHub** : `scope task new --issue <ref>` (`issue` côté MCP ; `123`, `#123`, `owner/repo#123` ou l'URL de l'issue) la lit par `gh issue view` ; titre, corps (6 000 caractères au plus) et labels ouvrent le brief, le record garde `issue` (numéro, URL, titre), la section Pull Request la montre et le fichier de contexte demande de la référencer depuis la PR (`Closes #123`). Donnée explicitement, elle doit se lire, sinon la création échoue. Sinon, la règle du point de départ s'applique : une URL d'issue que le prompt demande de travailler est une issue à coup sûr ; un `#123` nu est essayé comme PR puis comme issue ; une issue n'est jamais une branche de départ. La microsession peut aussi en nommer une (`issue` dans sa réponse, `gh issue view` et `gh issue list` dans son allowlist) : l'app la lit elle-même, jamais sur la parole du modèle.
- **Plusieurs tentatives sur un même brief** (best-of-N) : `scope task new … --attempts N [--models a,b,c] [--drivers x,y]` (`attempts`, `models`, `drivers` côté MCP), ou la molette *Attempts* de la feuille New Task, crée N tasks sœurs sous un topic nommé d'après le brief (`<nom> · attempt 1..N`), même prompt, une branche chacune (`<branche>-a1..N`), un thread chacune, modèle ou driver différent par tentative si demandé ; le record porte `attempt` (groupe, index, nom et branche de base). Toutes comptent dans le budget des agents : refus avec le nombre quand N dépasse ce qui reste (`3 attempts asked, but agents may open 2 more tasks`). Une task qui part d'une PR ou d'une branche existante est une seule tentative. La feuille **Compare attempts** (menu du topic, palette) met une colonne par tentative — état, tokens, temps d'agent, fichiers changés (+N −M), tests lancés lus dans la dernière réponse au mieux, premières lignes du livrable — et, dessous, le diff d'une tentative contre une autre (branches, commits seulement) ou contre la base (delta de la task, non commité compris), rendu par le parseur de Delta ; `1..N` choisit le côté gauche, `⇧1..N` le droit, `0` la base, lus sur la touche physique. **Keep this one** renomme la task choisie du nom du brief, déplace sa branche sur `<branche>` (`git branch -m`, upstream retiré, refusé si la branche existe déjà), lui retire le topic, archive les autres (branches et livrables gardés) et poste un item d'Inbox (`attemptsKept` sur le record) qui nomme les branches gardées. Depuis la liste de fichiers du diff, **Copy into…** copie un fichier d'une tentative dans une autre (copie fichier, suppression si la source ne l'a plus, refus hors sandbox ou à travers un lien) après avoir pris un checkpoint de la cible (raison `beforeCopy`), donc le fichier écrasé est à une restauration près. Logique pure et testée (`TaskAttempts`, `AttemptFileCopy`), git testé sur dépôts temporaires (`moveBranch`, `Delta.compare`, `keepAttempt`).
- **Mentionner une task passée** : `@task:<slug-ou-id>` et `@thread:<id>` dans un prompt (`task.new`, `thread.new`), un message (`thread.send`, Ask Orchestrator, réponse en ligne) ou la feuille New Task sont remplacés, avant d'atteindre l'agent, par un bloc entre `[Scope: context of task <slug> — begin]` et `… — end]` : nom, brief (1 500 caractères), branche, PR et état, topic, début de la dernière réponse gardée ou du rapport (`TaskDeliverableStore`), tasks archivées et clôturées comprises (même recherche que `scope task show`). Pour un thread : titre, task, état, dernière réponse. Expansion pure et testée (`TaskMention`) ; une mention sans réponse reste telle quelle, suivie d'une note. Les champs de message de l'app complètent `@` par les tasks du scope, récentes d'abord (`MentionQuery`).
- **Missions** : une task créée avec `--mission` (`mission: true` côté MCP, case *Mission* de la feuille New Task) a pour brief un objectif trop grand pour une task. Son record porte `mission.milestones[]` ; son fichier de contexte explique le protocole : découper l'objectif en jalons, chacun une task enfant avec une **étape de validation** (une commande shell — la suite de tests, un build, `gh pr checks <branche>`), n'ouvrir le jalon suivant qu'une fois le précédent validé. Scope stocke et valide, l'orchestrateur planifie : `scope task milestone add [<task>] "<titre>" --validate "<commande>" [--child <slug>]` nomme un jalon (`scope_task_milestone_add`), `scope task milestone done [<task>] <n|titre> [--child <slug>]` le marque fait (`scope_task_milestone_done`) — permis à un agent depuis la mission ou l'une de ses tasks, sans approbation, car rien n'est ouvert ni retiré. Au *done*, la commande de validation tourne dans la sandbox de la task enfant (celle de la mission sans enfant), avec `SCOPE_TASK`, `SCOPE_TASK_ROOT`, `SCOPE_SANDBOX`, `SCOPE_SCOPE`, `SCOPE_PORT`, 30 minutes au plus ; la réponse attend le verdict : `validated` (exit 0) ou `failed`, avec la fin du log (8 Ko) sur le record, et le log envoyé au thread du jalon (celui de l'enfant, sinon de la mission) par la même livraison qu'une review. Un jalon sans commande est atteint au *done* ; un jalon validé ne se remarque pas. La section Task montre la liste à cocher (état, commande, task enfant, sortie d'un échec au survol), la ligne de la sidebar la fraction `2/5`, le fichier de contexte la liste à jour. Opérations pures et testées (`Mission`). Les écritures concurrentes sur un record (le setup qui finit pendant qu'un jalon s'ajoute) se réappliquent l'une sur l'autre (`TaskManager.mutate`).
- **Teardown** : le champ `teardown` (carte du graph, config du scope) tourne dans chaque sandbox avant *Archiver* et *Clôturer*, avec les mêmes variables et 10 minutes de délai. S'il échoue, l'échec est montré et la suppression continue : le sweep de process qui suit arrête ce qu'il devait arrêter.
- **Cwd du thread** : la sandbox elle-même si la task n'a qu'un repo (les drivers attendent une racine git), la racine de task sinon.
- **Les autres sandboxes du thread** : un thread à la racine d'une task de plusieurs repos reçoit chaque sandbox active par l'argv `addDir` de son profil (`--add-dir <sandbox>` pour Claude Code), au lancement comme à la reprise ; un thread ouvert dans une sandbox reçoit les autres. Claude Code charge alors les skills, commandes et agents de chaque repo, et ses `CLAUDE.md` dès le départ (`CLAUDE_CODE_ADDITIONAL_DIRECTORIES_CLAUDE_MD=1` dans l'`env` du profil) — sans cela, rien de ce qui est un niveau plus bas n'est vu, et le `CLAUDE.md` d'un repo n'arrive qu'en annexe d'une lecture de fichier.
- **Ajouter un repo** à une task en cours : crée la sandbox manquante, la prépare, régénère `AGENTS.md` et le `.code-workspace`. Les threads déjà lancés la voient à leur relance ou reprise.
- **Archiver / clôturer une task** (`TaskManager.dismantle`, un seul pipeline pour l'UI, la CLI, le MCP, le Retry et le GC) : verrou par task (un second appel rejoint celui en cours), record persisté après chaque étape avec `cleanup` jusqu'à la fin. Ordre : threads raccrochés (groupe de process), teardown, sweep des process (cwd sous la racine de la task ou `SCOPE_TASK_ROOT`, SIGTERM puis SIGKILL après 3 s), sauvegarde des changements non commités, worktree renommé dans `sandboxes/.trash` et son dossier `.git/worktrees/<nom>` supprimé, racine supprimée. *Archiver* garde la branche et le record ; *Clôturer* supprime le record, et la branche si demandé.
- **Le livrable survit à l'archivage** : au moment où une task est archivée ou clôturée, la dernière réponse de chacun de ses threads (fin gardée, 64 Ko) et son fichier de rapport — `REPORT.md` à la racine de la task ou dans une sandbox, ou le fichier que nomme le champ optionnel `deliverable` du record (`scope task new --deliverable docs/study.md`, `deliverable` côté MCP), 1 Mo au plus, jamais hors de son dossier — sont écrits dans `tasks/deliverables/<id>.json`, avant que les sandboxes ne partent. Une reprise après échec complète le fichier sans rien effacer. La moitié des tasks sont des études sans PR : leur livrable est la réponse finale de l'agent, qui partait avec le thread. `scope task show <slug>` (`scope_task_show`, lecture seule, task ouverte, archivée ou clôturée) imprime le brief entier et ce qui a été gardé ; `scope summary` porte sur chaque ligne de task le début de cette réponse et les rapports gardés, `--task` les réponses elles-mêmes (fin, 6 000 caractères). Dans l'app, *Read deliverable* (section Task d'une task restaurée, palette pour une task archivée) l'ouvre dans la colonne de lecture.
- **Rien ne se perd, rien ne demande** : aucun dialogue pour un agent ni pour une task sans travail en cours ; l'UI demande seulement quand il y a quelque chose à perdre, et l'archive s'annule (§4.2 *Fermer sans regret*). Les changements non commités (suivis et non suivis, ignorés exclus, non suivis de plus de 50 Mo exclus et nommés) sont commités via un index privé sous `refs/scope/salvage/<slug>-<id>/changes-<time>` ; une branche non mergée supprimée à la clôture garde son dernier commit de la même façon. *Restaurer* rouvre une task archivée avec ces changements — depuis la notice d'archivage, la palette, ou par un agent (`scope task restore <slug>`, `scope_task_restore` ; `scope list` marque les tasks archivées). Pour un agent, restaurer compte dans son budget de tasks et suit la même approbation qu'en créer une. Un échec laisse la task hors de la sidebar, avec *Réessayer* ; le lancement suivant termine.
- **Des checkpoints par tour** : à chaque `turn.ended` ou `turn.failed` d'un thread d'une task, Scope prend un instantané de chaque sandbox de la task (`TaskCheckpoints`) — le même commit par index privé que le salvage (suivis et non suivis, ignorés exclus, non suivis de plus de 50 Mo exclus et nommés), parent `HEAD` de la sandbox, sous `refs/scope/checkpoints/<task-id>/<n>` dans le dépôt, message nommant le thread, le numéro du tour et la première ligne de la réponse. La branche ne bouge pas, l'index de la sandbox non plus ; jamais sur le checkout de base. Peu coûteux : rien si aucun arbre n'a changé depuis le dernier checkpoint (comparaison des hashes d'arbre ; une sandbox inchangée pointe sur le commit précédent sous le nouveau numéro), 3 s de debounce quand des tours se suivent, 50 gardés par task ouverte, 5 avec le record à l'archivage, tout supprimé à la clôture, et `scope gc` supprime ceux d'une task qu'aucun record ne nomme passé 30 jours (un Debug ne connaît pas les tasks de la release dans un dépôt partagé). Le journal est `tasks/<id>.checkpoints.json`. UI : dans la timeline, la barre d'un tour qui a laissé un checkpoint porte un point ; la section Task liste *Checkpoints* (heure, thread, première ligne, `+N −M` contre le précédent) avec, au survol, **Show diff** (colonne de lecture, checkpoint contre l'arbre de travail actuel, via le parser de Delta, en blocs `diff`), **Restore files** (`git restore --source=<commit> --worktree --no-overlay -- .` dans chaque sandbox après suppression des fichiers apparus depuis — jamais de reset de branche, jamais de commit touché ; l'état courant est lui-même checkpointé d'abord, c'est l'undo, la notice le nomme) et **Branch from here** (`<branche>-cp<n>` au commit du checkpoint, sans checkout). Aucun dialogue. CLI/MCP : `scope task checkpoints [<task>]` (`scope_task_checkpoints`, lecture seule), `scope task restore-checkpoint [<task>] <n>` (`scope_task_restore_checkpoint`) — un agent ne restaure que dans sa propre task (`AutomationPolicy.mayRestoreCheckpoint`), l'utilisateur partout, un agent hors Scope jamais. Tests sur dépôts temporaires : `TaskCheckpointTests`, `TaskCheckpointControlTests`.
- **Plusieurs pull requests par task** : une task porte toutes les PR que son travail a ouvertes — une par repo, deux sur une même branche (une fermée, une rouverte), une pile, une PR de docs à côté du prototype — dans `pullRequests[]` du record (numéro, URL, titre, repo, branches head/base, état et dates ; l'ancien champ `pullRequest` est encore lu). Chaque relecture interroge `gh pr list --state all --head <branche>` dans chaque sandbox, pour sa branche et celles que son reflog dit avoir visitées (`VisitedBranches`, 6 au plus, la branche par défaut exclue), puis `gh pr view` pour les liens que rien ne couvre plus. L'ordre est stable : les repos de la task dans leur ordre, puis le numéro, jamais l'état (`PullRequestSet.ordered`). La *primaire* — la première ouverte, sinon la première mergée, sinon la première — est ce qu'un bouton seul ouvre ; l'état de l'ensemble est `open` tant qu'une l'est, `merged` dès qu'une l'est et plus aucune ouverte, `closed` sinon (`aggregateState`). La ligne de la sidebar prend la PR *ouverte* la plus pressante (conflit avant checks rouges avant checks en cours…) et dit *PR merged* quand toutes sont réglées et une au moins mergée ; sa carte de survol et l'en-tête de la section Pull Request résument `2 PRs · 1 merged · 1 checks failing` ; la section liste une ligne par PR (repo, numéro, titre, état, checks, review) avec une sélection explicite gardée par task, et le détail, *Open on GitHub*, *Merge*, *Fix Conflicts* et *Send to Thread* portent sur la PR sélectionnée ; menu contextuel et palette ont une entrée par PR, nommée par son repo. L'Inbox fait un item par PR (`task:<id>:pr:<owner/repo/pull/n>`), *Since your last visit* compare chaque PR à son instantané (`scope-visits.json` v2), la frise marque chacune. `scope list tasks` a une colonne PR (`api #41 open ✗ · web #7 merged ✓`), `scope summary`, `task show`, `@task:` et le MCP donnent `pullRequests[]` (et `pullRequest` = la primaire). Logique pure et testée : `PullRequestSet`, `TaskStatus.decisive`, `VisitedBranches`.
- **Plusieurs branches dans une même task** : un repo d'une task porte, à côté de son worktree principal (celui de la branche de la task), une liste de worktrees secondaires (`TaskRepo.worktrees` : branche, chemin, base, état, salvage, date), chacun sur sa branche — la PR suivante d'une pile, une PR de docs à côté du prototype, sans quitter la branche en cours ni improviser un `git worktree add` que Scope ne connaîtrait pas. Les records antérieurs se lisent tels quels (liste absente = vide, et rien d'écrit tant qu'elle l'est). Le dossier est `<repo>@<branche-courte>` à côté du worktree principal (`api@fix-login` à côté de `api` ; pour un repo scope, dont la racine de task est le worktree, `<slug>@fix-login` à côté de la racine, sous le dossier du scope) : `@` n'apparaît jamais dans un slug ni dans un nom de repo, le nom se lit « repo à telle branche », et la branche courte est son dernier segment, remplacée par la branche entière slugifiée (puis `-2`, `-3`…) si une autre branche de la task a déjà pris le dossier. `scope task branch add [<task>] <branche> [--repo R] [--from <ref>|--pr <ref>]` (`scope_task_branch_add`) crée la branche depuis la base du repo, une branche existante ou la tête d'une PR, et son worktree ; le fichier de contexte est réécrit dans chaque worktree ; refus si la branche est celle de la task, déjà un worktree de la task, checkoutée ailleurs ou réservée ; `--repo` obligatoire sur une task de plusieurs repos ; même approbation que créer une task (une branche et un worktree écrits dans le repo de l'utilisateur), sans budget (un worktree n'ouvre aucun agent). `scope task branch list` (`scope_task_branch_list`, lecture seule) les énumère avec leurs PR ; `scope task branch remove [<task>] <branche> [--repo R]` (`scope_task_branch_remove`) raccroche les threads du worktree, sauve ses changements non commités comme l'archive (`refs/scope/salvage/<slug>-<id>/changes-<branche>-<time>`), le passe à la corbeille et garde la branche ; la branche de la task n'est pas retirable ainsi. `scope thread new --task T --branch B` ouvre un thread dans ce worktree (cwd), qui reçoit les autres sandboxes par `addDir`. Par défaut un agent appelle tout cela depuis sa task, sans la nommer. Chaque worktree est traité comme le principal : clé `TaskRepo.sandboxKey` (`<repo>` pour le principal, `<repo>@<branche>` pour un secondaire) dans les résumés de delta, le lag (`TaskLag.repos`), les checkpoints (ref `refs/scope/checkpoints/<id>/<n>-<branche-slug>` pour un secondaire, les deux worktrees d'un repo partageant le dépôt) et les journaux ; archive (salvage par worktree, dossiers retirés), restore (tout reconstruit, changements remis), clôture (`--delete-branch` supprime chaque branche), GC (les dossiers frères d'un repo scope sont possédés) ; follow-main mesure et rebase chaque worktree sur sa branche ; la découverte de PR interroge explicitement la branche de chaque worktree (plus seulement le reflog du principal), donc toutes les PR sont rattachées et l'archivage auto attend qu'elles soient toutes réglées. UI : la section Task liste une ligne par worktree (branche en chip pour un secondaire, au survol *New Thread* et *Remove*), le Delta et la carte de survol nomment `api · fix/login`, la section Pull Request montre la branche de chaque PR quand la task en a plusieurs et la sélection reste explicite ; *Add Branch…* dans le menu contextuel, la palette et l'en-tête de la section Task, *Remove Branch* dans le menu. Le fichier de contexte liste les worktrees secondaires sous leur repo et dit qu'une seconde branche se crée avec `scope task branch add`, jamais avec `git worktree add` ; le skill le répète. Tests : `TaskBranchTests` (migration d'un ancien record, nommage, ajout/retrait, archive puis restore avec deux worktrees sur un repo, clôture, GC d'un repo scope, checkpoints, PR sur les deux branches et archivage qui attend), `TaskBranchControlTests` (CLI, MCP, wire, approbation).
- **Pull requests en arrière-plan** : les PR de chaque task ouverte — liées, ou que sa branche pourrait porter (au moins un commit) — sont relues toutes les 5 minutes, deux tasks à la fois, l'ordre étalé sur l'intervalle, un échec doublant l'attente (jusqu'à 1 h), une PR mergée ou fermée relue toutes les 30 min ; rien en mode économie d'énergie. La task à l'écran garde sa boucle d'une minute. Planning pur et testé : `PullRequestRefreshSchedule`.
- **Archivage au merge** (préférence *Archive a task when its pull request merges*, activée par défaut) : quand une relecture voit l'ensemble des PR `merged` — plus aucune ouverte, une au moins mergée ; une task à deux PR attend que la seconde atterrisse ou soit fermée — la task est archivée par le même pipeline que la sidebar, avec une seule notice discrète *Archived <task>: pull request merged* et *Restore*, et le toast d'annulation (*“<task>” archived: pull request merged* — *Undo*, sans `⌘Z` : ce n'est pas un geste de l'utilisateur) — mais seulement quand plus rien ne la retient. Un merge dit qu'une branche a atterri, pas que la task est finie : une orchestratrice dont la propre PR merge pilote peut-être encore des tasks enfants. L'archivage est donc repoussé à la relecture suivante tant que (1) un thread de la task est en cours de tour, attend une réponse ou une permission, a échoué sur une erreur, se relance, a été coupé en plein tour par un redémarrage, ou a des sous-agents actifs ; (2) une task lancée depuis elle (`parentTask`), récursivement — une task archivée au milieu est traversée — est encore ouverte ; (3) une sandbox a des changements non commités, ou des commits que ni un remote ni la PR mergée ne portent (comptés après le `headRefOid` des PR de son repo — fork ou branche visitée compris, une tête absente du clone ignorée —, que GitHub donne et que le record garde (`GitClient.unpushedCommits`) : la branche distante supprimée et prunée après un squash merge ne fausse rien ; sinon contre `@{upstream}`, sinon contre `--remotes`) ; (4) Scope ne sait pas encore (sandbox pas mesurée, date de merge absente). Et (5) un thread qui a *commencé* un tour après le dernier merge — un message, une relance — dit que le travail a continué : la task reste ouverte jusqu'à ce que l'utilisateur ou son agent l'archive, ou qu'une autre de ses PR merge. Le tour qui a lancé `gh pr merge` a commencé avant le merge : il ne compte pas. Les commandes lancées en arrière-plan par un driver ne sont rapportées par aucun hook : elles ne retiennent la task que par le tour qu'elles relancent. Une PR fermée sans merge n'archive jamais. Une task restaurée alors qu'elle a une PR porte `keptOpenAfterMerge` et reste ouverte : le merge a pu arriver pendant l'archivage, sans être vu (`MergedTaskArchive`). Une task avec une PR reste donc ouverte jusqu'au merge : les agents n'ont plus à sonder GitHub, et n'archivent eux-mêmes que le travail sans PR.
- **Une task suit main** (préférence *When main moves*, par défaut *Ask the agent* ; surchargeable par scope dans `config.json`, champ `followMain`) : après chaque relecture de PR en arrière-plan, la sandbox de chaque task ouverte est `fetch`ée et sa branche mesurée contre `origin/<default>` — commits de retard, et conflits par un merge à blanc (`git merge-tree --write-tree`, git ≥ 2.38 ; en deçà, « conflicts unknown ») qui ne touche pas l'arbre (`BranchLag`, `TaskLag`). Le retard s'affiche dans la section Pull Request et la carte de survol (*behind main by 4 · conflicts in 2 files*), et dans `scope list tasks` (colonne MAIN). Puis, décision pure et testée (`FollowMain.decide`) : *Ask the agent* — quand la branche conflicte, ou que GitHub dit la PR `CONFLICTING`, le premier thread Claude/Codex vivant de la task (ouvert s'il n'y en a pas) reçoit, par la même livraison qu'une review, un message signé Scope qui dit ce qui a bougé (nombre de commits, PRs mergées lues dans les sujets, fichiers en conflit) et demande de rebaser sur `origin/<default>`, garder les deux côtés, régénérer, relancer les suites touchées une à une, rebuild, push avec lease, répondre une fois mergeable ; une fois par tête de main (`followedMainHead` sur le record). *Rebase when clean* — en retard sans conflit et sans thread en cours de tour, Scope lance `git rebase origin/<default>` dans la sandbox et pousse avec `--force-with-lease --force-if-includes` si la branche est publiée et la PR ouverte ; un rebase qui s'arrête est annulé, la branche vérifiée revenue où elle était, et l'agent sollicité. Jamais le checkout de base, jamais un arbre sale. *Never* — mesure et affichage seuls. Le menu contextuel d'une task porte *Don't Rebase Automatically* (`holdBranch` sur le record : ni rebase ni message, même à la demande) et *Rebase on Main Now*, comme `scope task rebase <task>` (`scope_task_rebase`, même approbation que créer une task) : le rebase propre ou le message, à la demande, quelle que soit la préférence.
- **Tasks dormantes** : une task ouverte sans activité de thread (fin de tour, outil, début de tour, création d'un thread, création de la task ; un relancement ne compte pas) depuis N jours (préférence, 3 par défaut, *Never* possible), ou dont la PR a été fermée sans merge, porte une légende `idle 4d` / `PR closed` dans sa ligne et, rangée par état, va dans le groupe *Dormant* — sauf si elle attend l'utilisateur ou travaille (`TaskDormancy`) Ce n'est qu'un classement : rien n'archive une task dormante ; seul le merge archive automatiquement (ci-dessus), et le ramasse-miettes (`collectGarbage`) ne touche qu'aux restes des tasks déjà archivées ou fermées.
- **GC automatique** (au lancement, toutes les 30 min, après chaque archivage ; préférence *Clean up automatically*) limité à `SCOPE_HOME` : process dont le cwd ou `SCOPE_TASK_ROOT` est sous `sandboxes/` hors task vivante, dossiers sans task (changements sauvés d'abord, grâce de 10 min, rien si un record est illisible), suppression des enregistrements git des seuls worktrees qui vivaient sous `sandboxes/` (jamais de `git worktree prune` global : il effacerait les worktrees de l'utilisateur sur un volume démonté), refs de salvage non référencées de plus de 30 jours. `scope gc [--dry-run]`.
- **Garde-fous** : avertissement si un repo a des submodules ou des hooks lourds (husky et consorts s'appliquent aux worktrees).
- **Hooks git des sandboxes** (`SandboxGitHooks`, `core.hooksPath` passé par `GIT_CONFIG_*` dans l'environnement du thread, jamais écrit dans un repo) : `pre-commit` refuse un commit dans le checkout de base ou dans la sandbox d'une autre task d'un repo de la task ; `pre-push` refuse un push depuis la sandbox vers la branche par défaut du remote. Un push de tags seuls (`refs/tags/v1.2.3`, aucune branche) passe : c'est ainsi qu'une release se coupe. La branche reste refusée même à côté d'un tag, donc `scripts/release.sh` — qui pousse `main` et le tag en un seul `--atomic` — échoue en bloc depuis une sandbox, sans rien publier à moitié.
- **Couper une release depuis un thread** (`scope release [X.Y.Z] [--repo R] [--dry-run] [--force]`, MCP `scope_release`, `ControlCall.release`) : c'est l'app qui release, pas le thread. `ReleaseRunner` (ScopeControl, testé avec un runner factice) lit la branche par défaut du remote (`git ls-remote --symref`, refus s'il n'en a pas), clone `origin/<default>` dans `SCOPE_HOME/releases/<owner-repo>/` (`--filter=blob:none` ; un clone existant est `fetch` puis `reset --hard`), vérifie avec `gh run list` qu'aucun workflow de release ne tourne et que la CI sur la tête est verte (`--force` passe outre ; sans `gh`, pas de vérification, dit dans la réponse), puis lance `scripts/release.sh [version] --yes [--dry-run]` du repo — ou, sans script, ce qu'il fait : `git cliff --bumped-version`, tag annoté, push du tag seul — avec l'environnement du shell de login de l'utilisateur, sans `SCOPE_*` ni hooks de sandbox, toute invite désactivée. La sortie du script revient ligne à ligne en `pending` et dans la réponse (`ReleaseResult`, bornée à 32 Ko, fin gardée). Approbation propre pour les agents (Settings › Automation › *Releases*, par défaut *After asking me* : seul endroit où le défaut d'autonomie s'inverse, une release ne se défait pas ; un `--dry-run` ne demande rien) ; le terminal de l'utilisateur n'est jamais interrogé.

### 4.4 Delta

Panneau unique, indépendant du driver, agrégé sur les repos de la task.

- **Trois modes** : *Task* (branche vs `merge-base` avec la base), *Non commité* (working tree vs HEAD de la sandbox), *Base vs origin* (ma base est-elle en retard ?).
- **Vue** : fichiers groupés par repo avec compteurs `+/-`, rendu unifié ou côte à côte, coloration syntaxique, repli des hunks, navigation clavier (`j`/`k`, `]`/`[` par fichier).
- **Actions** : ouvrir dans l'éditeur sur la ligne du hunk, révéler dans le Finder, copier le patch, commit (message pré-rempli depuis la task), push, *Créer la PR* (`gh pr create`, corps pré-rempli), *Ouvrir la PR* si elle existe.
- Rafraîchissement : FSEvents sur les sandboxes + `git status` throttlé.

### 4.5 Base

- Pour n'importe quel repo du scope : arbre de fichiers de la base, visionneuse en lecture seule avec coloration, recherche plein texte (`rg`), historique récent.
- *Pull* (fast-forward uniquement) ; indicateur "en retard de N commits".
- *Ouvrir un shell ici* : un terminal secondaire, sans driver, dans la base. Pour lancer les tests sur `main`, comparer un comportement, etc.
- *Ouvrir dans l'éditeur*.
- **Quel repo est montré.** Dans l'ordre : le repo épinglé dans le contexte courant, la ligne de repo sélectionnée, le repo où travaille le thread affiché (le dossier annoncé par son shell, ou celui du dernier fichier touché par l'agent, remonté par ses hooks), le repo du fichier ouvert dans le Delta, le premier repo de la task, le dernier repo montré dans le scope, le premier du scope. Le panneau dit laquelle de ces raisons s'applique.
- **Épingle.** Choisir un repo dans l'en-tête l'épingle pour le contexte courant — la task, le thread libre ou le scope — et seulement pour lui. Elle est visible, se retire d'un clic, et survit au redémarrage.
- **Essayer une task dans mon checkout** (préférence *Allow trying a task in my checkout*, **off par défaut**, surchargeable par scope dans `config.json`, champ `allowTryInCheckout`). Le cas d'usage : un serveur de dev lourd (une base de données, un port, un `node_modules`) tourne dans la base, et l'utilisateur veut y voir le résultat d'une task sans seconde installation. C'est l'exception au principe 3 (§1), et elle tient à quatre garanties. (1) *L'utilisateur seul* : menu contextuel / section Task → **Try in my checkout**, ou `scope task try <task>` depuis son propre terminal ; la commande est refusée à tout agent (thread Scope, agent externe), quels que soient les réglages d'automatisation, et le skill le dit. (2) *Réversible par construction* (`GitClient.beginTry`, testé sur des repos temporaires) : dans la base de chaque repo de la task, refus si une opération est en cours (rebase, merge, cherry-pick, revert, bisect) ou si des chemins sont en conflit (non stashables) ; sinon `git stash push -u -m "scope-try-<task>-<date>"` dont le SHA est retenu, mémorisation de la branche et du HEAD courants, puis `git switch --detach <branche de la task>` — détaché, donc la branche de l'utilisateur ne bouge jamais ; jamais de `reset --hard`. Un repo qui échoue après d'autres remet ceux-là en place : la task est essayée entière ou pas du tout. Refus si la base d'un repo est déjà sur une autre task. Les hooks git de la sandbox ne sont pas en jeu : la base garde les hooks de l'utilisateur. (3) *Visible* : la session (`trying: [{repo, previousHead, previousBranch, stashSHA, head, since}]` sur le record) s'affiche en bandeau proéminent sur la task **et** sur le panneau Base du repo (*Your checkout is on task X since 12:04 — Put back*), dans le badge du Dock (`try`) et la barre de menus. Les threads de la task continuent dans la sandbox ; la base est un miroir que l'utilisateur fait tourner. **Refresh** avance le checkout détaché sur la tête courante de la branche (switch si l'arbre est propre, `merge --ff-only` sinon). (4) *Put back garanti* (bandeau, menu, `scope task try --end`, et automatiquement à l'archivage ou la fermeture de la task et à la fermeture de Scope, sans confirmation ; marqué `endingAt` sur le record avant de commencer, et terminé au lancement suivant s'il a été interrompu) : les modifications faites dans la base pendant l'essai sont stashées à part et conservées, `git switch <previousBranch>` (ou détachement sur `previousHead` si la branche a disparu), `git stash apply <sha>` puis `drop` en cas de succès ; si l'application conflicte, le stash est **gardé**, le panneau Base s'ouvre sur le repo et un avertissement le dit — jamais de stash perdu.

### 4.6 Graph

- **Par repo** : `name`, `remote`, `default_branch`, `purpose` (une phrase), `stack`, `entrypoints`, `related` (dépend de / consommé par), `setup`, `test`, `tags`, `last_activity`.
- **Génération**, bouton *Analyser* :
  - Niveau 0, sans IA : README (premier paragraphe), manifestes (`package.json`, `Cargo.toml`, `pyproject.toml`, `go.mod`…), `git log` récent.
  - Niveau 1, avec IA : le driver par défaut en mode headless (`claude -p`, `codex exec`, `cursor-agent -p`) sur chaque repo, avec un prompt qui exige un JSON strict ; Scope valide le schéma avant d'écrire. Le `purpose` y est demandé comme la description d'un skill : une phrase, tirée de ce que fait le code (manifestes, arborescence, points d'entrée) et non recopiée du README, qui dit ce que fait le repo puis quand y travailler. Un repo inchangé n'est tenu pour fait que si sa carte vient du niveau demandé : l'analyse avec IA repasse sur ceux que seul le niveau 0 a décrits, et sur ceux qu'une version antérieure du prompt a décrits.
- **Cache** : clé = SHA de HEAD + hash du README + hash des manifestes. Édition manuelle possible et prioritaire sur la génération.
- **Vue** : cartes par repo en v1 ; une vue graphe des relations `related` quand le champ sera assez rempli pour la mériter.
- **Projection vers les drivers** : Scope écrit `AGENTS.md` (convention pivot, lue par Codex et Cursor) à la racine de task. Le profil Claude Code peut demander en plus un `CLAUDE.md` généré. Contenu : le contexte du scope tel que son propriétaire l'a écrit (réglages du scope), les repos de la task et leur rôle, les autres repos du scope avec leur rôle (pour que l'agent sache demander à en ajouter un), les règles (branche, ne pas toucher à la base).
- **Où** : le fichier est écrit là où démarrent les threads de la task (les skills et le `CLAUDE.md` de chaque repo leur parviennent par `addDir`, §4.3) — la sandbox quand la task n'a qu'un repo (y compris le cas mono-repo, où la racine de task *est* la sandbox), la racine sinon. Ailleurs, le driver ne le lit jamais.
- **Sous quels noms** : tous ceux que les profils déclarent (`context.file`, sauf `mode: none`), `AGENTS.md` toujours inclus — les threads d'une même task peuvent tourner sous des drivers différents. Même contenu dans chacun.
- **Fichier existant** : jamais écrasé, sauf s'il porte le marqueur de génération de Scope. Le nom laissé de côté est signalé dans le Problem Center : un agent qui démarre sans son contexte doit se voir.
- **Dans une sandbox** : chaque fichier écrit est ajouté à `.git/info/exclude`, donc le delta reste propre (décision ouverte 6 tranchée : fichier + exclude, tant qu'aucun driver n'expose de flag de contexte).

### 4.7 Adaptateurs et notifications

Un adaptateur transforme les événements d'un driver en états de thread. Mécanisme unique : le driver exécute une commande sur événement, cette commande est `scope-hook`, un binaire embarqué qui écrit `{thread, event, payload}` sur `scope.sock`, puis attend que l'app ferme la connexion (2 s au plus) : fermer dès l'envoi perdait un message sur dix, et la plupart des hooks que Claude Code lance au même instant (`PreToolUse` et `PermissionRequest`, `PostToolUse` et la status line).

- **Événements normalisés** : `turn.started`, `turn.ended`, `input.requested`, `permission.requested`, `thread.ended`.
- **Claude Code** (`claude-hooks`) : `permission.requested` vient de la notification `permission_prompt`, jamais du hook `PermissionRequest`. Celui-ci part avant que la boîte de dialogue ne s'ouvre, en même temps que les autres hooks `PermissionRequest`, dont n'importe lequel peut répondre à la place de l'utilisateur ; rien ne suit alors avant le `PostToolUse`, et un thread qui lance une longue commande restait `waiting` pendant toute sa durée. `permission_prompt` ne part que si la boîte est restée ~6 s ouverte (chaque frappe repousse le délai). Pour ne pas attendre ces 6 s, un `PermissionRequest` que personne n'a tranché au bout d'une seconde fait lancer une fois `claude agents --json` (~0,2 s, jamais en boucle) : si la session dit `status: waiting`, `waitingFor: permission prompt`, le thread passe `waiting` tout de suite (événement `permission.requested` de source `claude-agents`) — sidebar, Inbox, carte —, sans notification macOS : celle-ci attend le `permission_prompt`, comme avant, car la boîte s'ouvre pendant qu'un autre hook `PermissionRequest` (une app compagnon) décide encore. Pour la même raison, la session est redemandée chaque seconde jusqu'au `permission_prompt` (5 fois au plus) : si elle n'attend plus, un autre hook a tranché, la demande disparaît et le thread repasse `running` (vérifié avec un hook qui autorise au bout de 3 s : `waiting` 3 s, puis `running` pendant les 15 s de la commande). Limite : une réponse donnée ailleurs (une autre app) après la confirmation laisse le thread `waiting` jusqu'au `PostToolUse` ; un « No » dans la boîte n'envoie aucun hook, seul le `turn_duration` du transcript le dit, et le thread repasse alors `idle`.
- **Activité du thread** : chaque événement est aussi replié dans une `ThreadActivity` (`ScopeAdapters`) — dernier outil et sa cible (fichier, première ligne de la commande, motif, URL, description du sous-agent ; une ligne, 120 caractères au plus, extraite par `scope-hook` dans `payload["tool"]` / `payload["target"]`), tour en cours, les 200 derniers tours avec leur début, leur fin, leur issue (terminé, échoué, question, permission, interrompu, arrêté) et leurs appels d'outils (les 60 premiers, avec la durée de `PostToolUse`), la fin de la dernière réponse (16 Ko), la réponse en cours d'écriture (`saying` : les lignes que Claude Code remet par son hook `MessageDisplay`, événement `turn.said`, `payload["said"]` ; un message à la fois, 64 Ko au plus, jamais écrite sur disque, effacée à la fin du tour) et le chemin du transcript (`payload["transcript"]`). Un tour s'ouvre sur un prompt, ou sur le premier outil après une attente, et se ferme dès que l'agent s'arrête : une permission accordée ouvre donc un nouveau tour. Gardée à côté de l'enregistrement du thread, dans `<home>/threads/<id>.activity.json`, écrite à chaque fin de tour (pas à chaque outil) ; `scope list` en montre une ligne par thread (`activity`).
- **Limites de l'abonnement** : un abonnement Claude (Pro, Max) n'est pas un budget de tokens mais des fenêtres de temps — session glissante de 5 h, semaine, parfois une semaine par modèle — et c'est ce que le compteur montre en premier. Source : le JSON que Claude Code passe à sa *status line* à chaque réponse de l'assistant porte `rate_limits`, un objet par fenêtre (`five_hour`, `seven_day`, et ce que le forfait ajoute — `seven_day_opus`, `spend_limit` derrière une passerelle) avec `used_percentage` (0–100, au-delà une fois dépassé) et `resets_at` (epoch) ; présent pour les abonnés claude.ai seulement, après la première réponse de la session, et Claude Code retire une fenêtre une fois son `resets_at` passé (doc *statusline*). Le fichier de réglages par thread (`--settings`) déclare `statusLine` → `scope-hook statusline --stdin` quand le compteur est activé : le hook envoie `limits.reported` (payload `limits`, l'objet en JSON compact) puis lance la *status line* que les réglages de l'utilisateur nomment eux-mêmes — `.claude/settings.local.json` et `.claude/settings.json` du projet, puis `~/.claude/settings.json` (ou `$CLAUDE_CONFIG_DIR`), dans l'ordre de Claude Code — sur le même stdin et imprime sa sortie, donc rien ne change au bas du terminal (`SCOPE_STATUSLINE_NESTED` coupe toute récursion ; sans *status line* à l'utilisateur, la ligne reste vide ; les réglages *managed* passent avant et ne sont pas touchés). Rien dans `~/.claude` n'est modifié. Côté app, `RateLimits` (`ScopeAdapters`) parse l'objet, trie les fenêtres (connues d'abord), retire celles qui ont reset, choisit la plus serrée (pourcentage le plus haut, reset le plus proche à égalité), et classe le niveau (`calm` < 50 %, `watch` < 80 %, `tight` < 100 %, `exhausted`) ; le dernier rapport est gardé dans `<home>/limits.json` pour s'afficher dès le lancement, daté, et marqué périmé au-delà de 30 min (l'usage depuis claude.ai ou une autre machine n'y est pas). Le forfait est lu dans `~/.claude.json` (`oauthAccount.organizationRateLimitTier` → *Max 20×*, *Max 5×*, *Pro*… ; `ClaudeAccount`, lecture seule) ; un compte API/console (pas d'`oauthAccount`, jamais de `rate_limits`) garde tokens et coût comme information principale. Jamais de chiffre inventé : sans rapport, le compteur dit *unknown*. Bande en bas de la sidebar : fenêtre la plus serrée, anneau, `31% · 35 min`, barre colorée selon le niveau ; clic → popover : chaque fenêtre avec pourcentage, barre, *resets in*, dollars pour un `spend_limit`, puis les tokens en secondaire. `scope ping` et `scope list` (`limits`, et dans les outils MCP `scope_ping` / `scope_list`) donnent par fenêtre pourcentage, `resetsAt`, `resetsIn`, niveau et la plus serrée, pour qu'un agent ralentisse près du plafond. Un thread ouvert compteur coupé doit être relancé pour rapporter. Testé dans `RateLimitsTests`, `ClaudeAccountTests`, `ClaudeStatuslineTests`, `ClaudeHooksAdapterTests`.
- **Tokens consommés** : toutes les 30 s, `TokenLedgerStore` (`ScopeAdapters`) lit ce que le transcript de chaque thread Claude Code (`ThreadActivity.transcriptPath`) a gagné depuis la dernière lecture — à partir de l'offset retenu, hors du main thread, jamais écrit — et somme le `message.usage` de chaque appel (entrée, sortie, écriture et lecture de cache, avec le modèle et l'heure). Une réponse écrite en plusieurs lignes (une par bloc de contenu, même `message.id`) compte une fois ; les transcripts des sous-agents (`<session>/subagents/*.jsonl`) comptent pour leur thread, puisqu'ils consomment le même quota. Le total affiché inclut les lectures de cache. Fenêtres glissantes : 5 h, aujourd'hui, 7 jours ; par thread, task et scope. Gardé dans `<home>/tokens.json` : le détail minute par minute 8 jours, le total de chaque thread 90 jours après son dernier appel, threads fermés compris (un transcript reste au thread qui l'a lu le premier). `scope list` donne `tokens` par thread (`1.2M · 5h`), `scope summary` le total par task et par thread. Dans l'app : la bande en bas de la sidebar (5 h sans limites rapportées ; popover avec 7 jours, scopes, threads les plus gourmands) et le total de la task dans son bandeau et sa carte de survol. Les tokens disent qui a dépensé les limites ci-dessus ; sans limites rapportées (clé API), ils restent l'information principale, consommation seulement, sauf budget saisi par l'utilisateur (*tokens per 5 h*) qui fait du compteur une jauge. Coût équivalent API (table de prix par famille de modèle, `TokenPricing`) derrière une préférence, désactivée par défaut.
- **Un tour terminé le reste** (`ThreadActivity.isLate`) : après `turn.ended` / `turn.failed`, seul un prompt (`UserPromptSubmit`, y compris la fin d'une tâche de fond que Claude Code soumet comme prompt) ouvre le tour suivant. Un outil (`PostToolUse` d'une commande ou d'un sous-agent en arrière-plan) ou une demande (`Notification` d'une permission déjà tranchée) qui arrive ensuite ne change pas l'état ; pas plus qu'un événement envoyé (`sentAt`) avant la fin du tour mais livré après. Après une attente (question, permission) ou un Esc, l'outil suivant reprend le tour comme avant.
- **Sous-agents** (`ClaudeSubagents`, `ScopeAdapters`, dans `ClaudeSession.subagents`) : chaque sous-agent lancé par un thread Claude Code (outil `Agent`, ex-`Task`) avec son id (`agentId`), son type, sa description, son modèle (`resolvedModel`), en arrière-plan ou non, son état (en cours, terminé, échoué, arrêté, interrompu), début, fin, durée, tokens, nombre d'appels d'outils, le début de son rapport (2 000 caractères), son transcript, son worktree (`isolation: worktree`), sa profondeur (`spawnDepth`) et le sous-agent qui l'a lancé quand un hook le dit. Sources recoupées, dans n'importe quel ordre : l'appel `Agent` (hook `PostToolUse` et transcript : `async_launched` avec l'`agentId` tout de suite, `completed` avec les totaux pour un sous-agent au premier plan), `SubagentStart` / `SubagentStop` (`agent_type`, `agent_transcript_path`, `last_assistant_message` ; ceux à `agent_type` vide sont des agents internes de Claude Code, ignorés), la `<task-notification>` de fin (statut, `result`, `usage`, worktree) et `agent-<id>.meta.json` à côté du transcript du sous-agent (lu par l'app, une fois, tolérant). L'`agentId` du résultat, l'`agent_id` des hooks et le nom du fichier sont le même id ; un fait qui ne nomme que l'appel (`tool_use_id`) est fusionné dès qu'un autre nomme les deux. Un sous-agent en arrière-plan n'est fini que par sa notification : son `SubagentStop`, et une notification `completed` dont le résumé dit *is waiting on its own background work*, ne sont que des réponses d'étape. Aucun sous-agent ne survit à son process : la fin de session (`SessionEnd`) ou un transcript relu par un process plus récent (début du process, ou dernier `SessionStart` hors compaction) le marque *interrompu*. Rien n'est écrit : une relance reconstruit la liste depuis le transcript ; 50 au plus par session, les finis les plus anciens partent d'abord. `ThreadActivity.agents` compte toujours ce que les hooks disent en cours (jamais écrit, borné à deux heures) ; `thread.wait` en retire ceux dont le transcript a vu la fin et y ajoute ceux lancés par le process en cours dont le `SubagentStart` s'est perdu (`ClaudeSubagents.runningCount`). Un tour qui se termine alors qu'un sous-agent tourne en arrière-plan (« Waiting for 3 background agents ») ne termine pas `thread.wait` : le thread reste au travail (`agents` dans la réponse) jusqu'à ce qu'ils rapportent et qu'il réponde ; la fin du dernier, vue par un hook ou dans le transcript, vaut attente d'un tour (`startGrace`), et une réponse écrite avant elle (« waiting for 1 background agent », ou le rapport d'étape d'un sous-agent) ne termine pas l'attente (`subagentsEndedAt`). Une question, une permission ou la sortie du process terminent l'attente malgré tout. L'archivage au merge compte de la même façon. **Sidebar** : sous la ligne du thread (ou de la task qui le représente), une ligne compacte par sous-agent en cours, et pendant 90 s par sous-agent qui vient de finir : sa description et une seule pastille d'état (en cours qui respire, fini, échoué, anneau pour arrêté ou interrompu), quatre lignes au plus puis *N more running* ; un clic sélectionne le thread et ouvre la carte. **Carte Subagents** (panneau de droite, tasks) : fermée, `1 running · 4 done` ; ouverte, une ligne par sous-agent, le plus récent en haut (pastille, description, type · modèle · durée · tokens · outils), groupée par thread quand la task en a plusieurs ; un clic déplie le détail — début du rapport, ses derniers outils lus dans son propre transcript (`ClaudeSubagentTail`, incrémental, 20 derniers, relu toutes les 2 s tant qu'il tourne), son worktree, *Reveal its transcript in Finder*. Aucune action n'arrête un sous-agent. **CLI/MCP** : `scope list threads` (colonne SUBAGENTS, champ `subagents` : ceux en cours et les 5 derniers finis), `thread wait` (même champ, par thread), `thread read` (tous, avec le début de chaque rapport, entre marqueurs non fiables). Testé dans `ClaudeSubagentsTests`, `ClaudeSubagentTailTests`, `SubagentSummaryTests`.
- **Session Claude Code** (`ClaudeSession`, `ScopeAdapters`) : ce que Claude Code fait au-delà du tour — tâches de fond, sous-agents, mode de permission, compactions, serveurs MCP —, à côté de `ThreadActivity` et pas dedans : l'activité ignore ce qui arrive après la fin d'un tour (`isLate`), alors que c'est justement là que finissent une commande en arrière-plan ou un sous-agent. Deux sources. (1) Chaque événement porte le stdin du hook entier, borné par `scope-hook` pour toujours tenir et toujours se parser (`payload["hook"]`, chaînes ≤ 2 000 caractères, tableaux ≤ 100, 48 Ko au plus, resserré sinon ; `ClaudeHookFacts` : `permission_mode`, `effort`, `agent_id`/`agent_type`/`agent_transcript_path`, `tool_input`, `tool_response`, `background_tasks`, `session_crons`) ; les hooks qui ne font qu'informer — `PreCompact`, `PostCompact`, `PermissionRequest`, `PermissionDenied`, `PostToolUseFailure`, `PostModelSwitch`, `Elicitation` / `ElicitationResult` qui décrivent un formulaire MCP (demandes en attente, ci-dessous), et `TaskCreated` / `TaskCompleted` qui nourrissent le plan de l'agent (carte *Plan*) — arrivent en `driver.reported`, qui ne bouge aucun état (`scope-hook` ne répond rien : la boîte de permission s'ouvre comme sans lui). (2) Le transcript, lu de façon incrémentale (`ClaudeTranscriptTail`, depuis l'offset de la lecture précédente, lignes complètes seulement, hors du main thread) 300 ms après chaque événement et toutes les 3 s : `<task-notification>` (dédoublonnées, Claude Code les écrit jusqu'à trois fois), `task_status`, appels et résultats des outils qui lancent ou arrêtent du travail de fond ou posent une question, `compact_boundary`, `permission-mode`, `deferred_tools_delta` (serveurs MCP), `pr-link`, `cost-state`, `turn_duration`. Format non documenté : un type ou une clé inconnus sont ignorés, jamais une erreur. Rien n'est écrit sur disque ; une relance relit le transcript depuis le début. Testé dans `JSONValueTests`, `ClaudeHookFactsTests`, `ClaudeTranscriptTailTests`, `ClaudeSessionTests`.
- **Serveurs MCP** (`ClaudeMCPServers`, `ClaudeSession.mcpServers`) : pour chaque serveur, nom, source (`user`, `local`, `project`, `plugin`, `claude.ai`), transport, état (`pending`, `failed` avec message et `errorCode`, `needsAuth`, `connected`, `unknown`), outils listés et appels comptés. Claude Code ne dit jamais qu'un serveur est connecté : chaque `deferred_tools_delta` donne un instantané des listes qu'il porte (une liste absente ne dit rien — `needsAuthMcpServers` manque presque toujours), et Scope *infère* `connected` (`isInferred`, `evidence`) quand ses outils `mcp__<serveur>__*` sont listés, qu'un a été appelé (`PostToolUse`), ou qu'un serveur connu ne figure plus dans aucune liste ; un serveur qui ne liste que `authenticate` est `needsAuth` inféré. Avant le premier delta, un serveur déclaré est `unknown`. Config déclarée lue en lecture seule à chaque `SessionStart`, hors du main thread : `~/.claude.json` (`mcpServers`, `projects[<cwd>].mcpServers` moins `disabledMcpServers`) et `.mcp.json` du dossier (serveurs approuvés seulement) — nom et transport, jamais commande, URL, en-têtes ni env. La carte Connectors de l'inspecteur le montre.
- **Compactions** (`ClaudeCompactions`) : la liste vient des `compact_boundary` du transcript (quand, `auto`/`manual`, tokens avant/après, durée ; dédoublonnée, relue à la relance) ; « en cours » de `PreCompact` jusqu'à `PostCompact`, la frontière, un `SessionStart` `compact` ou la fin du tour. Pendant ce temps, la ligne d'activité du thread dit *Compacting…*, au travail comme au repos.
- **Modèle et mode** (`ClaudeSessionModel`, `ClaudeSession.permissionMode`) : le modèle courant vient de `SessionStart.model` puis de chaque `PostModelSwitch.to_model` (un sous-agent garde le sien) ; le sous-titre de la fenêtre dit `Claude Code (Fable 5.1) · Plan mode` — le mode n'y figure que s'il n'est pas `default`.
- **PR ouvertes par l'agent** (`ClaudeSessionPullRequests`) : `gitOperation.pr` du `PostToolUse` d'un `Bash` (`gh pr create`, `gh pr merge` : le transcript ne garde pas le résultat d'une commande au premier plan) et `pr-link` du transcript, une entrée par PR. Une PR nouvelle ou un changement d'action depuis le lancement de l'app redemande à `gh` les PR de la task 2 s plus tard (`refreshTaskPullRequest`, puis l'archivage si mergée) au lieu d'attendre le passage de fond ; le modèle de PR reste celui de la task.
- **CLI / MCP** : `scope list threads` (et `scope_list`) porte `session` par thread Claude Code (`ClaudeSessionSummary` : `permissionMode`, `model` courant, `effort`, `compacting`, `compactions`, `lastCompaction`, `mcpServers` en échec ou à authentifier) ; le tableau montre le modèle courant, une colonne `MODE`, et ajoute à l'activité `compacting`, `2 compactions`, `MCP failed: …`. Testé dans `ClaudeMCPServersTests`, `ClaudeMCPConfigTests`, `ClaudeCompactionsTests`, `ClaudeSessionModelTests`, `ClaudeSessionPullRequestsTests`, `ClaudeSessionSummaryTests`.
- **Tâches de fond** (`ClaudeBackgroundWork`, dans `ClaudeSession.background`) : les commandes `Bash` passées en arrière-plan (`run_in_background`, ou au timeout : `timedOutAfterMs`, le début reculé d'autant), les Monitors, le réveil `/loop` (`ScheduleWakeup` : `scheduledFor`, raison, prompt ; effacé par le prompt qui le déclenche ou par `stopped`) et les crons de la session (`CronCreate` / `CronDelete` : id, `cron`, `humanSchedule`, prompt, récurrent). Une tâche `b…` : genre (shell, monitor), commande, description, fichier de sortie, début et fin, état — en cours, terminée avec son code de sortie (lu à la fin du `summary` : `completed (exit code N)`, `failed with exit code N`, `script failed (exit N)`), échouée, tuée, arrêtée, expirée, finie (sans dire comment) — et pour un Monitor son échéance (`timeoutMs`) et ses 5 derniers événements. Sources : le `PostToolUse` et l'appel du transcript pour le lancement (un appel refusé, sans id, ne lance rien ; un sous-agent garde les siens) ; `<task-notification>` pour la fin (une notification de reprise peut nommer plusieurs tâches, `Task ids: …`, toutes arrêtées ; l'expiration d'un Monitor est un événement `[Monitor expired …]` sans statut) ; `TaskStop`, qui n'écrit aucune notification ; `task_status` ; l'instantané `background_tasks` / `session_crons` du `Stop` principal, qui fait autorité : une tâche absente n'est plus en cours, un cron absent est supprimé — sauf liste coupée par `scope-hook` (longueur égale à une borne). `SessionEnd` ou la sortie du process arrêtent tout (un Monitor passé son échéance expire). Les tâches `a…` (sous-agents) et `k…` (MCP) sont ignorées. Les terminées au-delà de 20 sont oubliées, les plus anciennes d'abord. Carte *Background* du panneau de droite : par thread de la task, les tâches en cours (commande, durée, temps restant d'un Monitor), puis les 5 dernières terminées (code de sortie), puis le programmé ; un clic montre la fin du fichier de sortie (64 Ko au plus, `FileTail`, hors du main thread, relue toutes les 2 s tant qu'elle est affichée ; fichier disparu → message). Arrêt depuis la ligne, après confirmation : Scope envoie SIGTERM puis SIGKILL au groupe de process de la tâche, trouvé parmi les descendants du process du thread (`BackgroundProcess`, `ScopeCore`) — le shell dont stdout/stderr est `tasks/<id>.output`, sinon celui qui fait `eval '<commande>'` (Monitor), rien si zéro ou plusieurs candidats. Choisi plutôt que `/tasks` de Claude Code (liste pilotée au clavier, dans un ordre que Scope ne peut pas relire) ou qu'un message demandant `TaskStop` (un tour de l'agent, et seulement quand il est libre) ; Claude Code rapporte ensuite la tâche `failed (exit 144)`, affichée *stopped*, et l'agent peut décider de la relancer. Réveils et crons : aucun process, pas d'arrêt. Rien dans la sidebar. `scope list threads` (colonne *BACKGROUND* quand une tâche tourne), `thread read` et chaque entrée de `thread wait` portent `background` (`BackgroundTaskSummary`) ; l'attente ne les attend jamais — un serveur de dev ou un Monitor de 30 min la ferait courir jusqu'à son délai — elle les rapporte. Testé dans `ClaudeBackgroundWorkTests`, `BackgroundWorkReportTests`, `BackgroundProcessTests`, `FileTailTests`.
- **Demandes en attente** (`ClaudePendingRequests`, `ScopeAdapters`, valeur de `ClaudeSession`) : ce qu'un thread Claude Code demande, avec son contenu — une permission (la commande Bash entière, bornée à 4 000 caractères, et sa description ; le fichier et la nature de l'édition ; l'URL, la recherche ; l'outil MCP et son serveur, `mcp_server` ; les règles que Claude Code propose de retenir, `permission_suggestions`, en mots), une question (`AskUserQuestion` : chaque question, son `header`, ses options `label`/`description`, `multiSelect`), un plan (`ExitPlanMode` : le plan et `planFilePath`), une élicitation MCP (serveur, message, mode, URL, champs du formulaire). Sources : `PermissionRequest` décrit la permission mais ne la montre pas — elle reste *non confirmée* tant que `permission_prompt` (ou `claude agents`, ci-dessus) ne dit pas que la boîte est ouverte, si bien qu'une permission tranchée par l'auto mode ou un autre hook n'est jamais affichée ; le `PreToolUse` des outils à question montre la question tout de suite ; `Elicitation` décrit le formulaire, `elicitation_dialog` le montre (les hooks `Elicitation` et `ElicitationResult` rejoignent les hooks informatifs). Fin : le `PostToolUse` / `PostToolUseFailure` / `PermissionDenied` du même `tool_use_id`, à défaut du même outil avec la même entrée (`PermissionRequest` ne porte pas d'id), `ElicitationResult`, le tour qui bouge (`UserPromptSubmit`, `Stop`, `StopFailure`, `SessionEnd`, un `turn_duration` du transcript écrit après la demande), la touche de l'utilisateur dans la boîte (un chiffre, ↩, Esc ; `1` remet le thread `running` sans attendre la fin de l'outil). Deux permissions demandées ensemble s'affichent l'une après l'autre, dans l'ordre (`1 of 2`) : le `PostToolUse` de la première laisse le thread `waiting` sur la seconde. Affichage : la ligne du thread dans la sidebar (`Asks to run git push`, `Asks to use probe_echo on probe`, la question elle-même, `Plan: …`, `probe asks: …` ; une ligne, le tout en aide), l'Inbox, la notification et une carte au-dessus du terminal (`PendingRequestCard`) qui montre la commande en entier, les options d'une question, le plan, le formulaire. **Répondre depuis Scope** : *Allow* / *Deny* sur une permission (carte, Inbox, notification), un clic sur l'option d'une question (cases et *Submit Answers* pour un choix multiple ou plusieurs questions). Scope tape les touches qu'on taperait — vérifié sur Claude Code 2.1.304 : `1` est toujours *Yes*, Esc vaut *No* quel que soit le nombre d'options intermédiaires, le chiffre d'une option répond à une question à choix unique, chaque chiffre coche une option d'un choix multiple, → passe à la question suivante et le `1` de la revue envoie les réponses (`ClaudeDialogAnswer`) — et seulement après avoir lu le bas du terminal et y avoir trouvé cette boîte-là (son invite, la commande ou le fichier ou le serveur, la question et sa première option ; pas la commande d'une autre permission affichée plus haut) ; sinon rien n'est tapé et la carte dit pourquoi. Un plan (ses options changent avec les réglages) et un formulaire MCP se répondent dans le terminal. L'Inbox et la notification d'une permission n'offrent plus *Reply* : le ↩ du texte tapé choisirait le *Yes* en surbrillance ; la notification n'offre *Allow* que si elle montre la commande entière. La réponse n'est pas exposée aux agents (CLI/MCP) : `scope thread read` et chaque entrée de `scope thread wait` donnent `pendingRequest`, pour qu'un orchestrateur sache ce qui bloque, et le skill lui dit de ne pas taper dans la boîte. Testé dans `ClaudePendingRequestsTests`, `ClaudeAgentsReportTests`, `ClaudeDialogAnswerTests`, `ThreadActivityHeadlineTests`, `ThreadNotificationSaidTests`, `ThreadReadTests`.
- **`thread.send --wait`** (MCP `wait: true`, `timeout`) : le message tapé et soumis, l'app enchaîne le même `thread.wait` sur ce thread et renvoie son résultat dans la réponse du send (`ActionResult.wait`) : un appel au lieu de deux. Sans `↩` (`--no-enter`), refusé.
- **Pull request dans les réponses** (`PullRequestSummary` : numéro, URL, état, checks, mergeabilité, review, brouillon, `checkedAt`) : `scope list tasks` (colonne PR), `task.show` et chaque entrée de `thread.wait` (avec l'id de la task) la portent, telle que `gh pr view` l'a vue en dernier ; à la fin d'une attente, la PR de la task de chaque thread terminé est redemandée à GitHub si le dernier regard date de plus de 30 s. L'agent n'a plus à lancer `gh pr view` / `gh pr checks` pour savoir où en est le travail.
- **`thread.wait`** : une réponse arrivée pendant l'attente la termine ; et un thread `running` dont la dernière réponse est plus récente que le dernier `turn.started` (prompt ou outil) est tenu pour terminé — l'état repasse à `done`. Filet de sécurité réservé aux drivers qui signalent le début d'un tour (pas Codex). Gardée à côté de l'enregistrement du thread, dans `<home>/threads/<id>.activity.json`, écrite à chaque fin de tour (pas à chaque outil) ; `scope list` en montre une ligne par thread (`activity`).
- **Notifications macOS** sur `input.requested`, `permission.requested`, `turn.ended` si l'app n'est pas au premier plan, avec actions *Répondre* / *Aller au thread* / *Voir le delta*. Badge = threads en attente.
  - Le corps cite l'agent : la question qu'il pose (`AskUserQuestion`, le plan d'`ExitPlanMode`, le message d'une élicitation MCP précédé de son serveur, le message d'un `Notification` qui n'est pas la phrase standard), sinon la fin de sa dernière réponse si elle date du tour en cours ; pour `turn.ended`, le début de la réponse ; pour `permission.requested`, ce qui est demandé (`Said.request`) : la commande telle quelle (ni Markdown retiré, ni `*` mangé), sinon l'outil MCP et son serveur, le fichier, l'URL. Blancs écrasés, ~180 caractères coupés sur un mot ; le constat (« needs your answer », « asks for a permission ») passe en sous-titre. `turn.failed` garde ses mots. La notification d'une permission que Scope sait répondre porte *Allow* (si la commande tient entière) / *Deny* / *Go to Thread* au lieu de *Reply*. Préférence *Show what the agent said* (activée par défaut) pour revenir au corps générique.
  - *Répondre* (`UNTextInputNotificationAction`, bouton *Send*) tape la réponse dans le thread par le même chemin que `thread.send` (origine utilisateur, ↩ inclus), sans ramener l'app au premier plan, puis retire la notification. Une réponse vide n'envoie rien ; un échec remplace la notification par « Reply not sent ».
- **Commandes du driver** (`thread.send --command`, MCP `command: true`) : un message envoyé par `thread.send` arrive sous une ligne de signature (`[Scope: message from thread …]`), que le driver lit comme de la prose — `/model …`, `/clear`, `/compact` n'y survivent pas. Avec `--command`, le texte est tapé tel quel, sans signature, et soumis avec ↩ : il est destiné aux commandes slash du driver lui-même. Permis depuis le terminal de l'utilisateur ; pour un agent, seulement vers les threads qu'il a ouverts (et leurs descendants), sauf si *Réglages ▸ Automation ▸ Driver commands* (`automation.commandReach`, même valeurs que `threadReach`, `own` par défaut) ouvre tous les threads — jamais plus large que *Talking to threads*.
- **Sans adaptateur** : `running` tant que le process vit ; heuristique regex sur la sortie, désactivée par défaut.
- Les adaptateurs sont déclarés dans les profils de driver, donc extensibles sans recompiler.

### 4.8 Ouvrir dans l'éditeur

Geste de premier rang, partout, toujours sur le **bon checkout** : la sandbox si on part d'une task ou d'un thread, la base si on part de la vue Base.

- **Éditeur par défaut** : détecté au premier geste (Zed, Cursor, VS Code, Sublime, JetBrains, Nova, dans cet ordre ; ceux qui tournent déjà d'abord), enregistré, réglable. Aucun point d'entrée n'est grisé faute d'éditeur. Un éditeur connu est piloté à sa façon — son outil en ligne de commande est pris dans le bundle de l'app, pas sur le `PATH` — ; tout autre est un template libre : `{path}`, `{file}`, `{line}`.
- **Une fenêtre par checkout, retrouvée** : rouvrir un checkout revient à sa fenêtre au lieu d'en créer une (`zed -e`, comportement natif de Cursor / VS Code). On passe toujours la racine du checkout, jamais le sous-dossier où le thread s'est déplacé.
- **Cible résolue selon le contexte** : depuis un thread → sa sandbox (dans une task à plusieurs repos, celle où l'agent a touché un fichier en dernier ; la task entière à défaut), ou le repo qui contient son dossier pour un thread libre ; depuis Base → `<scope>/<repo>/` ; depuis un fichier du Delta → la sandbox **et** le fichier, sur la ligne, pour qu'il s'ouvre dans son projet ; depuis le Graph → sélecteur si le repo a plusieurs checkouts (base + N sandboxes), avec branche et état de chacun.
- **Task entière** : Cursor / VS Code → `<task-root>/<slug>.code-workspace` (un dossier par sandbox) dès qu'il y a plusieurs sandboxes, la sandbox seule sinon ; Zed, Sublime → les sandboxes côte à côte dans une fenêtre ; les autres → le dossier racine.
- **Points d'entrée** : barre de titre du thread, survol d'une ligne de task, clic droit sur un repo, icône sur chaque fichier du delta, palette, `⌘E` (repo courant), `⌘⇧E` (task entière). `⌥`-clic copie le chemin.

### 4.9 Usage de l'app

Pour savoir ce qui sert vraiment dans Scope — et ce qui ne sert jamais — l'app tient un journal **local** de son propre usage. Rien ne quitte le Mac : ni réseau, ni SDK, ni tiers. Activé par défaut ; *Réglages ▸ General ▸ Usage* le coupe (*Record how I use Scope*) et efface l'historique (*Clear History*).

- **Journal** : `<home>/usage/usage-YYYY-MM.jsonl` (mois UTC), un événement par ligne `{at, kind, id, source, scope?, context?, duration?}`. `kind` ∈ `click`, `shortcut`, `menu`, `palette`, `notification`, `control`, `view`, `setting`. Jamais de chemin, de prompt, de texte du terminal, de nom de repo ou de branche : des ids d'éléments et de méthodes, le scope par son UUID, une préférence par sa clé (pas sa valeur). Écrit par un acteur (`UsageRecorder`, `ScopeCore`) qui reçoit les événements par un flux — le thread principal ne fait qu'enfiler —, écrit toutes les 5 s et à la fermeture, plafonne un mois à 8 Mo et supprime au lancement ce qui a plus de 180 jours.
- **Ids** : `<zone>.<élément>`. Les contrôles de l'app (`Controls.swift`, `IconButtonStyle`) comptent un clic dans la zone où ils sont dessinés (`.usageArea` : `sidebar`, `inspector.delta`, `sheet.graph`, `settings.terminal`…) sous leur `.usageID`, sinon `<zone>.button`. Les commandes du menu sont lues sur `NSMenu.didSendActionNotification` (menu principal seulement ; `shortcut` si un `keyDown` les a déclenchées) et partagent leur id `command.<…>` avec la ligne de palette de la même commande. Le reste : sélection d'une ligne de la sidebar à la souris, balayage entre scopes, sections de l'inspecteur et feuilles (temps à l'écran), lien ⌘-cliqué dans le terminal, fichier ouvert depuis Delta, revue envoyée, actions de notification, et chaque appel CLI/MCP (méthode, appelant agent ou utilisateur).
- **Temps à l'écran** (`ScreenTimeClock`, `ScopeCore`, testé) : le chrono d'une section ou d'une feuille ne tourne que quand quelqu'un peut la regarder — app au premier plan, une fenêtre de l'app visible (occlusion, ni masquée ni réduite), session déverrouillée, Mac éveillé, et une frappe ou un mouvement de souris dans les 2 dernières minutes (`CGEventSource.secondsSinceLastEventType`, sondé toutes les 10 s ; l'inactivité est datée de la dernière entrée, donc le seuil ne décide que de ce qui est une pause, jamais de ce qui est compté). Chaque pause coupe un segment, logué tout de suite (`context: active` pour le premier d'une ouverture, `resumed` pour les suivants) ; le rapport compte une ouverture par segment `active` et n'additionne que les durées des segments datés. Les événements `view` d'avant (sans `context`) restent dans le journal mais leurs durées sont ignorées — une section laissée ouverte une nuit en comptait quarante-sept heures — et le rapport dit depuis quand la mesure vaut (`screenTimeSince`, premier segment `active`).
- **Registre** : `<home>/usage/registry.json`, chaque élément dessiné ou déclaré au moins une fois (menu principal parcouru au lancement), pour pouvoir dire ce qui n'a *jamais* servi.
- **Lecture** : `scope usage [période] [--area A] [--limit N] [--json]`, outil MCP `scope_usage` (lecture seule, permis aux agents comme `summary`). Mêmes périodes que `scope summary`. Réponse : éléments les plus utilisés, par zone ; éléments jamais utilisés sur la période ; clavier / menu / palette / souris par commande ; appels agent / utilisateur par méthode ; temps passé par feuille et section ; tendances face à la période précédente de même durée ; et les `limits` (ce que le journal ne peut pas savoir).

### 4.10 Assist

Un assistant qui **ne tourne que sur événement** — fin de tour, question, thread `running` depuis plus de 4 min, création de task — lit la fin du terminal et répond par des **étiquettes**, jamais par une action. La sortie du terminal est une donnée non fiable : elle est citée entre les marqueurs de `thread.read`, sous le même avertissement, et le modèle n'a aucun outil.

- **Deux étages** (`ScopeAssist`, testé ; AppKit et FoundationModels restent dans l'app) :
  - *étage 0* : Apple Foundation Models (`FoundationAssistModel`, macOS 26, `SystemLanguageModel.default`), gratuit et local, bon pour classer en sortie structurée (`@Generable`), 4 k tokens de contexte, une session par appel (le transcript d'une session garde chaque réponse, une deuxième queue n'y tiendrait plus), `prewarm()` au lancement ;
  - *étage 1* : le modèle léger du driver via un **nouveau gabarit sans outil** du profil, `headlessAssist` (`claude -p {prompt} --output-format json --model haiku --tools "" --setting-sources "" --strict-mcp-config --no-session-persistence`, `{prompt}` avant les flags variadiques). Jamais `headlessLight`, qui autorise `gh` et `git`. `HeadlessAssistModel` refuse un argv qui n'est pas prouvé sans outil (`--tools ""` présent, ni `--allowedTools` ni `--dangerously-skip-permissions`). Il sert de second avis sur un verdict « bloqué » du local, et de repli quand le local est indisponible, sous un **plafond quotidien** (40 par défaut) tenu dans `<home>/assist.json`.
- **Jobs** (`AssistJobs`), chacun un schéma et une consigne : `ThreadDigest {activity, stuck, reason}`, `NotificationTriage {kind ∈ blockingQuestion, informational, failure}`, `ArchiveHint {looksFinished, reason}`, `TopicPick {topic}` parmi les topics existants du scope (un choix hors liste est ignoré).
- **Déclencheurs** (`AssistTriggers`, fonction pure de l'événement, des threads, du dernier passage et de l'heure) : digest d'un thread `running` dont le tour a plus de 4 min, puis toutes les 8 min au plus ; tri sur `turn.ended`, **avant** la notification, une fois par 30 s par thread, et seulement quand le verdict peut changer quelque chose (`triageMatters` : app en arrière-plan et préférence *quiet informational* active — une question notifie toujours, et rien ne part quand l'app est devant) ; indice d'archivage sur `turn.ended` d'une task sans PR dont la réponse ressemble à un livrable (≥ 200 caractères, ne finit pas sur une question) ; topic à la création d'une task sans topic quand le scope en a. L'entrée est la fin du terminal, ANSI retiré, ≈ 3 k tokens au plus (`TranscriptTail`).
- **Mémoire** (`AssistMemory`, testé) : par thread, l'empreinte de ce que chaque job a lu en dernier et son verdict. Les mêmes mots (un `Stop` et sa copie tardive, un thread qui redit sa réponse) reprennent le verdict sans appel, sans événement d'usage et sans seconde notification ; un digest n'est redemandé que si la fin du terminal a changé hors sa dernière ligne (spinner, compteur) ; un nouveau tour oublie la fin lue. Avant : 586 appels en deux jours, un par fin de tour et un par 4 min par thread `running`, sans regarder si quelque chose avait changé ni si le verdict servait.
- **Ce qui s'affiche** : la ligne d'activité du thread prend les mots du digest pendant le tour ; un verdict « bloqué » devient *Seems stuck — raison* dans la sidebar, un élément de l'Inbox et une notification ; *Not stuck* (Inbox, menu contextuel) efface la marque et compte un faux positif ; une fin de tour notifiée parce que l'assistant l'a lue comme une question ou un échec porte l'action *Not Blocking* (catégorie `thread-triaged`), qui marque le thread lu, retient les mots comme informatifs et compte un faux positif ; une fin de tour classée informationnelle ne notifie pas (préférence) ; *Looks finished — archive?* dans le bandeau de la task, proposition avec son ✕ ; le topic choisi est posé sur la task si personne ne l'a fait entre-temps.
- **Réglages ▸ Assist** : *Off* / *On-device only* (défaut) / *On-device + Haiku* avec le plafond ; disponibilité des deux modèles ; appels du jour par étage, dernière latence, faux positifs ; les trois décisions débrayables.
- **Journal** : chaque classification réelle va dans le journal d'usage (`kind: assist`, `assist.<job>.<verdict>`, `context` = étage ou `false-positive`), jamais le texte lu ; un verdict repris de mémoire n'y va pas.
- **Mesuré** (M1 Max, macOS 26.5, `swiftc` non signé) : contexte 4096 ; digest ≈ 1,2 s à chaud, 1,7–4 s aux premiers appels d'un processus ; 6/6 digests justes sur les deux queues de la note de recherche, 2/2 tris justes.

### 4.11 Prompts programmés

Des prompts que Scope envoie de lui-même, sur une règle, pendant qu'il tourne — il tourne déjà en continu avec son menu bar.

- **Un schedule** appartient à un scope (`schedules[]` de sa déclaration dans `config.json`) : nom, règle (`hourly` à une minute, `daily` / `weekdays` à une heure, `weekly` un jour à une heure), prompt, cible (l'orchestrateur du scope, ou une nouvelle task avec un driver et un modèle), actif ou en pause, et son dernier run (heure, issue `replied` / `noReply` / `failed`, première ligne de la réponse, thread, task). Réglages › Automation › Schedules (un sélecteur de scope) et la feuille de réglages du scope les éditent : ajouter, modifier, mettre en pause, lancer maintenant, retirer. À la création, deux exemples sont proposés, en pause : *Morning: PRs with red checks* (jours ouvrés, 9 h, à l'orchestrateur) et *Evening: summarize today* (18 h 30, `scope summary today`).
- **Le planificateur** est pur et testé (`Scheduler`) : les occurrences viennent de `Calendar.nextDate` sur les composantes d'horloge, jamais d'une addition de secondes, donc un 9 h quotidien reste 9 h le jour du changement d'heure. Chaque minute, un schedule actif part si une occurrence est passée depuis que l'app surveille (son lancement) et que son dernier run ne la couvre pas. Au lancement, préférence *Catch up at launch* (activée par défaut) : une occurrence quotidienne, de jours ouvrés ou hebdomadaire manquée dans les dernières 24 h part une fois (le Mac dormait à 9 h) ; une horaire attend l'heure suivante.
- **L'envoi** : vers l'orchestrateur, le prompt est tapé par le chemin d'*Ask Orchestrator…* (un thread arrêté est démarré pour le recevoir), sous une ligne `[Scope: scheduled prompt “<nom>” — …]` qui dit que la première ligne de la réponse est ce que l'utilisateur lira ; vers une task, `task.new` avec le driver et le modèle du schedule, le titre `<nom> · <date>`, une branche `schedule/<slug>` nommée par Scope (pas de microsession), le topic `schedules`. Le run est noté sur le schedule dès l'envoi (`noReply`), pour que la minute suivante ne le relance pas, puis complété quand le tour du thread finit (même règle que `scope thread wait`, 30 minutes au plus) : `replied` et la première ligne de la réponse. Un envoi impossible (pas d'orchestrateur, task refusée) est `failed`, avec la raison, et va au Problem Center.
- **L'Inbox** reçoit chaque run comme une entrée *Schedule <nom> ran — <première ligne>* (trois jours, ou jusqu'à *Mark read*), avec *Open* (le thread), *Read reply* (`v`, la réponse dans la colonne de lecture) et *Mark read* ; un run sans réponse pointe vers le thread, un run raté dit pourquoi.
- **CLI / MCP** : `scope schedule list [--scope S]` (`scope_schedule_list`) — règle, cible, prochaine occurrence, dernier run — et `scope schedule run <nom> [--scope S]` (`scope_schedule_run`), qui lance maintenant, même en pause, répond ce qui est parti et laisse la réponse à l'Inbox ; pour un agent, la même approbation que créer une task. Un nom présent dans plusieurs scopes demande `--scope`.

Les mécanismes d'événements changent vite : à vérifier contre la doc de chaque outil au moment de l'implémentation.

**Claude Code est le driver de référence.** Les profils Claude Code (`claude-code`, `claude-code-bypass`) reçoivent toutes les features construites sur ses hooks, son transcript et sa *status line* : sous-agents, tâches de fond, contenu des demandes en attente, serveurs MCP, compactions, mode de permission. Les autres colonnes du tableau décrivent un support maintenu tel quel : il n'est ni retiré ni étendu, et une feature propre à Claude Code n'a pas d'équivalent à leur trouver. Ce qui suit vaut pour Claude Code sauf mention contraire ; la liste de ce qu'il expose et de ce que Scope en fait est dans `docs/research/claude-native.md`.

`addDir` est répété pour chaque répertoire supplémentaire du thread (§4.3), `{dir}` valant ce répertoire ; il vient après l'argv `prompt`, parce qu'un flag variadique comme `--add-dir` placé avant prendrait le prompt pour un répertoire. Absent, le thread ne voit que son cwd. Seuls les profils Claude Code le déclarent pour l'instant.

**Driver.** Un thread ou une task ouvert sans nommer de driver (`⌘T`, `thread.new`, `task.new`, un schedule, une tentative, follow-main, le graphe) tourne sur le driver de *Réglages ▸ Default driver* ; vide (*Automatic*), sur le premier profil agent installé, jamais le shell (`DriverChoice`). Une seule exception : en mode *Automatic*, le `⌘T` de l'utilisateur reprend le driver qu'il a ouvert en dernier dans ce scope, pour ne pas redemander. Cette mémoire est une commodité de l'interface, pas un réglage : elle ne sert jamais à ce qu'un agent, la CLI ou le MCP ouvrent, et ne l'emporte jamais sur une préférence posée. Un thread qu'un agent ouvre n'hérite pas du driver de son parent — un agent qui veut le sien le passe (`--driver`) ; il hérite de son modèle seulement s'il tourne sur le même driver (ci-dessous). Un modèle ne remplace jamais le profil : il s'ajoute à ses flags et à son env (`claude --dangerously-skip-permissions --model …`), reprise comprise — un profil par modèle est inutile et perd les flags du profil de base.

**Modèle.** `modelArgs` dit comment le driver reçoit un modèle, `{model}` valant celui du thread : ajouté après `args` au lancement et après l'argv `resume` à la reprise — avant le prompt, le flag ne prend qu'une valeur — et après un argv `headless` quand l'appel en donne un (les appels headless d'aujourd'hui, graphe et proposition de task, n'en donnent pas ; `headlessLight` garde son modèle léger). Claude Code, Codex et Cursor prennent `--model` ; le shell n'a pas de `modelArgs` et refuse un modèle. `models` liste ceux que les menus proposent (*New Thread With Driver ▸ Claude Code ▸ …*, palette, Réglages) ; tout autre nom passe quand même par *Other Model…* ou `--model`.

Le modèle d'un thread est fixé à son ouverture (`thread.new --model`, `task.new --model`, MCP `model`) et gardé sur son enregistrement (`ThreadRecord.model`), donc Relaunch et la reprise le repassent ; il s'affiche dans le sous-titre de la barre d'outils et dans `scope list threads`. Précédence quand rien n'est passé, dans l'ordre : le modèle de l'agent appelant, s'il ouvre un thread de son propre driver (un modèle Claude ne dit rien à Codex) ; le défaut du scope (feuille de réglages du scope, `ScopeDeclaration.model`) ; le défaut du driver (*Réglages ▸ Drivers ▸ Default model*, `preferences.driverModels[<driver>]`) ; sinon le driver choisit (`ModelChoice`, `ScopeDrivers`). Les résidents (orchestrateur) suivent les défauts du scope et du driver.

Un driver custom = un fichier JSON dans `~/.scope/drivers/`. Contribuer un driver au projet = ouvrir une PR avec ce fichier et, si besoin, un adaptateur.

## 6. Architecture technique

**Stack**

- Swift 6, SwiftUI pour l'app, AppKit là où SwiftUI ne suffit pas (terminal, splits, menus contextuels).
- **SwiftTerm** pour le PTY et le rendu terminal.
- Git par `Process` sur `/usr/bin/git`, pas de libgit2 : comportement identique à ce que tu tapes, hooks respectés. Un acteur `GitClient` sérialise les commandes par repo.
- `gh` optionnel pour PR et liste des repos d'org.
- Coloration : Highlightr, tree-sitter si le besoin de précision se confirme.
- Persistance : JSON sur disque, pas de base de données. Tout ce qui est visible depuis un terminal est dans `~/.scope/`.
- Notifications : `UserNotifications`. Watchers : FSEvents.
- Distribution : hors App Store (PTY + binaires arbitraires → pas de sandbox macOS), signé Developer ID + notarisé, Homebrew cask. Sparkle pour les mises à jour.
- Licence : à choisir (MIT ou Apache-2.0).

**Modules**

```
Scope
├── Scopes       déclaration, découverte des repos, watchers
├── Git          GitClient, worktrees, parser de diff
├── Drivers      profils, lancement PTY, env, reprise
├── Threads      état, onglets, cycle de vie
├── Tasks        création, sandboxes, AGENTS.md, .code-workspace, clôture
├── Graph        génération L0/L1, cache, projection
├── Adapters     socket unix, événements normalisés → états
├── UI           Sidebar, TerminalPane, Inspector (Graph / Delta / Base), Palette
└── scope-hook   binaire CLI embarqué, appelé par les hooks des drivers
```

**Garde-fous**

- `scope-hook` n'accepte que les événements portant un `SCOPE_THREAD` connu.
- Aucune commande git destructive sans confirmation (`worktree remove` avec changements, `branch -D`, `reset --hard`).
- Scope ne stocke aucun token : `gh` et les drivers gèrent leur propre auth.
- La protection de la base est une convention (les agents travaillent dans les sandboxes), pas une garantie système. La doc le dit clairement.

## 7. Interface

Le raisonnement, les options écartées et ce qui a été construit sont dans `docs/design/INFORMATION_ARCHITECTURE.md`. Squelette :

- **Trois colonnes à plat** sous une seule barre d'outils, séparées par des filets : sidebar, scène, inspecteur. Pas de panneau flottant, pas de matériau translucide. Chaque filet se tire sur une bande de 10 pt (le trait reste de 1 px, le curseur de redimensionnement couvre toute la bande) et un double-clic ramène la dimension à sa valeur de départ : largeur de la sidebar, de l'inspecteur, moitié pour la colonne de lecture, parts égales entre deux listes de l'inspecteur. Couleurs de la charte par défaut — fond Ivory et cartes blanches en clair, fond Onyx et surfaces marine en sombre, accent Electric (Periwinkle en sombre) ; un jeu de gris neutres reste un réglage. Le terminal garde ses propres couleurs.
- **Sidebar** : le travail du scope courant — threads libres, puis tasks avec leurs threads. Une ligne dit ce qui se passe en mots (*waiting for your permission*, *an agent is working*). **Lignes compactes par défaut** (28 pt : le nom, et un seul indicateur à droite — le point d'état des threads, ou un chip `merged` quand les PR de la task sont mergées ; plus d'icône de driver ni de glyphe d'état à gauche, le terminal dit déjà quel driver tourne et le point dans quel état, le glyphe reste dans la carte de survol) ; une task qui attend ou travaille prend une seconde ligne (42 pt) le temps que ça dure, qui dit ce que fait son agent. `⌃⌘L` passe en lignes détaillées : deux lignes partout. Aucun compteur `+N −M` dans la ligne — à 264 pt ils tronquaient le nom ; ils restent dans la carte de survol, l'inspecteur et le bandeau de la task. **Rangée par état par défaut** à l'installation (groupes *Needs you*, *Working*, *Finished, not read*, *Quiet*, *Dormant*, chaque en-tête avec son compte, un groupe vide sauté) ; l'arbre par topic reste un réglage (`⌃⌘G`), et un choix déjà enregistré dans `config.json` est gardé — seul le défaut d'une installation neuve change. Un filet vertical de 1 px, pendu sous le chevron d'une task (ou de *Loose threads*), relie ses threads imbriqués, qui s'alignent sous son nom, avec un tiret vers chacun. Le point d'état a sa colonne de 18 pt, qui coupe son halo : l'animation ne sort jamais du fond arrondi de la ligne sélectionnée. Logique pure et testée : quelles lignes ont une seconde ligne, le chip, l'ordre et les comptes des groupes (`SidebarRowLayout`, `SidebarGroup`, `SidebarTaskRowPolicy`). Une task oubliée le dit (`idle 4d`, `PR closed`) en tête de sa seconde ligne, avant l'activité de l'agent, ou après son nom sur une ligne compacte. La ligne sélectionnée est un fond gris arrondi qui garde les couleurs du texte. En lignes détaillées, la seconde ligne d'un thread dit ce que fait son agent dès que son driver l'a rapporté : l'outil en cours en mots (*Editing TaskTopic.swift*, *Running swift test*, *Searching "topic"* ; le chemin réduit à son dernier composant, entier dans l'aide au survol), ce qu'il demande quand il attend (la question, ou *Asks to run swift test* quand le driver nomme l'outil ; la notification `permission_prompt` de Claude Code n'en nomme aucun, la ligne dit alors *Waiting for your permission*), puis comment son tour a fini et depuis quand (*Finished · 3m ago* — un réglage montre plutôt la première ligne de sa réponse). L'heure avance par pas de 30 s dans la seule légende. Une task à un seul thread prend cette ligne tant que l'agent travaille, attend ou a un résultat non lu ; ensuite son propre état en dit plus. La barre de titre reprend la phrase tant que l'agent travaille ou attend. Une task lancée depuis une autre n'est pas imbriquée sous elle — elles partagent en général un topic, qui les rassemble déjà : en arbre, tant qu'aucun de ses agents ne travaille ni n'attend, sa seconde ligne commence par *from <parent>*, un lien qui sélectionne le parent ; la carte de survol du parent liste les tasks lancées depuis lui, et le menu contextuel mène de l'un à l'autre. La section *Repositories*, repliée par défaut, annonce le nombre de repos modifiés. Pas de boutons *Nouveau thread* / *Nouvelle task* en bas de la sidebar (le réglage qui les montrait a disparu ; son ancienne clé `showSidebarFooter` est ignorée à la lecture) : `⌘T`, `⌘⇧T`, la palette, la CLI et l'orchestrateur suffisent, et le bas de la sidebar est à la bande d'usage, collée au bord, sans espace mort.
- **Scopes** : chaque scope est une tuile dans l'en-tête de la sidebar — sa première lettre sur une couleur à lui, une icône ou une image choisies. L'image est copiée sous le home, réduite à un carré de 128 px en PNG, et tient toujours dans le carré de la tuile : une photo le remplit, un logo sur fond uni y est posé entier sur ce fond, une image transparente est posée sur une plaque (ou dessinée comme la lettre, sur la couleur, quand c'est un pictogramme d'un seul ton). Une seconde image peut la remplacer en apparence sombre. On la choisit, on la colle ou on la dépose — sur la tuile ou dans les **réglages du scope**, une feuille qui réunit son nom, sa tuile, le contexte donné aux agents, la profondeur de découverte et son graph. Le scope courant porte son nom ; les autres tiennent à côté tant qu'il y a de la place, le reste derrière un compteur `+N`. Une marque au coin dit ce qui s'y passe : un thread attend, un tour a échoué, un résultat n'est pas lu, des agents travaillent ; rien si rien ne se passe. Les tuiles suivent l'anneau des scopes, dans l'ordre déclaré à partir du scope courant : la première est le scope suivant, la dernière le précédent — là où mène un balayage. Quand la place manque, le réglage choisit seulement lesquelles restent (les plus urgentes, ou les plus proches) ; le suivant et le précédent gardent toujours la leur. Changer de scope ramène là où on en était : la ligne, le thread, les sections ouvertes de l'inspecteur.
- **Depuis ta dernière visite.** Un scope est *regardé* tant qu'il est courant et l'app au premier plan ; quand ça cesse (autre scope, app à l'arrière, quitter), l'heure et l'état des PR de ses tasks sont notés dans `<home>/scope-visits.json`. Au retour — en changeant de scope, ou quand l'app revient devant après N minutes (20 par défaut) — si quelque chose a bougé, une ligne discrète sous l'en-tête de la sidebar le dit, sur une seule ligne tronquée en fin : *Since 11:40 — 1 question for you · checks failing on api-cache · PR merged on token-refresh · 2 turns finished*. Ce qui attend le propriétaire d'abord, quatre fragments au plus (le reste en *+N more*) ; les tours se comptent par leur date, les PR par différence avec l'état noté au départ (des checks déjà rouges ne sont pas une nouvelle). Chaque fragment mène au thread ou à la task ; une task déjà archivée ouvre sa PR. Pas de modale, pas de focus volé : la bande part au premier changement de sélection, après dix secondes vues, ou avec sa croix. Rien n'a bougé, rien ne s'affiche. Réglages › Général la coupe et règle N. L'agrégation est une fonction pure testée (`ReturnDigest`).
- **Lire la réponse de l'agent.** La réponse d'un thread — celle qu'il est en train d'écrire quand son driver la remet au fil de l'eau (en-tête *writing…*, la colonne suit la fin du texte), sinon la dernière — rendue en Markdown natif (titres, listes, tables, code, citations ; aucune image ni contenu distant chargé, le HTML reste du texte) dans la colonne de lecture : `⌘⇧R`, le bouton de la barre d'outils, *Read Reply* dans le menu du thread, ou un clic sur la légende *Finished* d'une ligne détaillée. Un lien web va au navigateur, un chemin — lien ou code `` `Sources/App.swift:12` `` — s'ouvre comme un lien du terminal, tout autre schéma (`javascript:`, `data:`…) reste du texte. *Copy as Markdown* dans l'en-tête, Échap ferme. La colonne de lecture s'ouvre avec ou sans l'inspecteur : elle parle du thread, pas des listes de la task. Autour de la réponse : *This turn*, les outils du tour (nom, cible, durée, depuis `PostToolUse` ; un outil inconnu de Scope s'affiche pareil), *Changes*, le checkpoint que le tour a laissé (+/−, ouvre son diff), et *Earlier in this session*, les tours précédents lus dans le transcript JSONL de Claude Code (`TranscriptReader` : quelques clés lues, tout le reste ignoré, jamais une source d'état ; illisible, la liste le dit). Un tour cliqué s'affiche avec son prompt en citation ; les blocs qui ne sont pas du Markdown connu (HTML, conteneurs `:::`) restent bruts, montrés tels quels. Le parseur de blocs (`MarkdownDocument`) et la politique des liens (`MarkdownLink`) sont dans ScopeKit, testés ; l'inline passe par `AttributedString`.
- **Liens du terminal.** Un `⌘`-clic sur un chemin ou un lien `file://` (OSC 8) qu'un agent affiche ouvre le fichier dans la colonne de lecture : la copie de la sandbox si le thread appartient à une task, celle de la base sinon, le fichier lui-même s'il est ailleurs, à la ligne indiquée. Un chemin relatif est cherché depuis le dossier du thread, puis à la racine de chaque repo de la task — l'agent omet souvent le nom du repo ; si plusieurs fichiers correspondent, l'en-tête les propose. Un fichier modifié par la task offre son diff. Un lien web va au pane Browser de la task ou au navigateur système selon `BrowserRoute` (ci-dessous).
- **Ce qu'ouvre un agent ne prend pas l'écran.** Un thread ou une task ouverts par un agent apparaissent dans la sidebar avec leur état, mais ne remplacent le terminal affiché que si aucun thread n'est à l'écran dans ce scope (réglable : jamais, toujours).
- **Scène** (centre) : le terminal du thread sélectionné. Barre de titre : le chemin *scope › task › thread*, puis driver · dossier · état · *Ouvrir dans l'éditeur*.
- **Inspecteur** (droite, masquable) : sous une bande de 30 pt qui nomme le sujet (la task, sinon le repo montré par *Repository*) et porte la **barre des panes** (Overview, Details, Changes avec le nombre de fichiers en badge, Shell, Browser, Pull requests avec le nombre de checks rouges, Files, `⋮`), une colonne de **cartes** repliables sur **deux pages** (`InspectorPlacement`). **Overview** dit ce qui se passe : *Plan*, *Changes*, *Pull requests*, *Subagents*, *Background*, *Artifacts*, chacune seulement quand elle a quelque chose à dire (un plan, des fichiers changés, une PR liée, un sous-agent qui tourne, une commande de fond ou un cron, un rapport, un fichier écrit ou une page publiée — les checkpoints seuls ne comptent pas), toujours dans cet ordre quel que soit l'ordre d'arrivée. **Details** (`⇧⌘D`, icône ⓘ) range ce qu'on va chercher : *Environment*, *Context*, *Connectors*, puis les cartes d'Overview tant qu'elles sont vides, puis *Repository*, *Files*, *Search*, *History*. Une carte qui monte ou descend apparaît ou s'efface en fondu sur place (coupé sous Reduce Motion) ; une carte qui redevient vide reste **trois minutes** sur Overview avec son état final (*finished 2m ago* pour Background, `4 done` pour Subagents), comptées depuis la fin réelle de la commande ou du sous-agent, puis descend ; une carte ouverte sur Overview y reste jusqu'à ce qu'on la replie ou qu'on change de task. Quand une carte est descendue pendant qu'on ne regardait pas Details, son bouton porte un point discret à la couleur d'accent, effacé à l'ouverture de Details — jamais un compteur. Overview vide dit *Nothing happening yet* avec un lien *Show Details* ; sur Overview, une carte vide épinglée n'a pas de paragraphe d'explication, il reste sur Details. Seule sur Overview, Changes prend toute la hauteur. La page n'est pas mémorisée : un lancement repart sur Overview. Raccourci et commande : *Go ▸ Details* (`⇧⌘D`, affiché dans l'overlay ⌘), et la palette. Chaque carte répond à une question (où ça tourne, ce qui a changé, ce qui est livré, ce qui a été produit, ce que l'agent a reçu) et dit une chose par ligne : un glyphe monochrome à gauche, un nom, une valeur à droite. Une carte est un panneau à bord de 1 px et rayon 8 sur le fond, titre en casse de phrase, 8 pt d'air entre deux ; fermée, son résumé se lit à droite du titre. Le `⋮` ouvre le menu *Cards* : pour chaque carte, *When it has something* (ou *In Details* pour les cartes de référence), *Always in Overview* (épinglée, même vide — Environment épinglée passe en tête) ou *Hidden* (sur aucune page ; la dernière visible ne peut pas être masquée), et *Reset to defaults*, mémorisé par scope avec les cartes ouvertes ; `⌘D` sur une carte masquée la fait revenir. Un clic sur un bouton de la barre ouvre la carte, sur la page où elle est, *et* son pane quand elle en a un (le diff pour Changes, le fichier pour Files) ; Overview revient à sa page et ferme le pane. *Environment* dit une chose par ligne : la bande de version, une ligne par worktree, le **setup** (la commande en mono, son état en puce à droite — en cours avec les secondes qui défilent, ✓ ou ✗ avec la durée ; un clic ouvre le journal dans la colonne de lecture ; rien quand les repos ne déclarent pas de setup), les **ports** (`Ports · block 4310–4319`, les puces `localhost:PORT ↗` de ceux qui écoutent, sinon *nothing listening*) puis, sous les puces, une ligne par **process** qui écoute sur un port du bloc — point, ligne de commande tronquée au milieu, à droite le thread qui l'a lancé ou son pid — lus par `lsof` tant que la carte est ouverte, au rythme des ports ; en pied, `This Mac · 312 MB on disk · 2 h 14 of agent time`. Fermée, son en-tête ajoute *setup running* / *setup failed* quand c'est le cas ; *Pull requests* montre une ligne compacte par PR (glyphe d'état, titre, `repo #n · +a −d · ✗ 1 / 4 · review`), le détail de celle choisie, et en pied ce qu'elle attend de toi (*Ready to merge*, *2 checks failing*, *Conflicts with the base*) avec *Ask the agent* — conflits, log du check ou merge partent au thread en une phrase, jamais un bouton git ; *Context* s'ouvre sur le brief, replié à quatre lignes (titres et filets sautés), avec *Read in full* qui l'ouvre dans la colonne de lecture — il n'attendait avant que dans la carte de survol — et le topic en pastille ; puis *Given to the agent* : une ligne par fichier de contexte là où démarrent les threads — ceux que Scope écrit sous chaque nom que lisent les drivers installés (`AGENTS.md`, `CLAUDE.md` ou son compagnon `CLAUDE.local.md`), et ceux du repo lui-même — avec sa taille, un clic l'ouvrant dans la colonne de lecture, et les skills présents dans les sandboxes (`.claude/skills`, copiés à l'installation ou commités) en pastilles ; puis *Model* : le modèle du thread courant de la task (sinon le premier qui en a un) et la version du driver, une **jauge de contexte** (barre fine, pourcentage) quand le driver dit à quel point sa fenêtre est pleine — la status line de Claude Code le fait, relayée par `scope-hook statusline` avec les limites —, et dessous les tokens lus, écrits et la part servie par le cache (`184k in · 22k out · 61 % cached`). Fermée, la carte dit `Fable 5.1 · 38 %`, sinon le modèle, sinon la longueur du brief. *Artifacts* dit ce que la task a produit hors de son diff, en quatre groupes : *Report* (le `REPORT.md` de la racine ou d'un sandbox, ou le fichier déclaré par `--deliverable`, avec son âge, `+N` depuis le dernier checkpoint quand le sandbox en a un, un aperçu des premières lignes rendu en Markdown dans un encadré, et *Read* qui l'ouvre dans la colonne de lecture ; à défaut, ce que l'archive a gardé) ; *Files written this task · outside the repo diff* (chaque cible de `Write` / `Edit` / `NotebookEdit` et chaque redirection `>` d'un `Bash`, rapportées par les hooks, qui n'est pas dans le diff git : hors des worktrees, dans un dossier ignoré, ou un binaire — image, PDF ; une ligne par fichier, chemin coupé au milieu, tour et taille, la plus récente en tête, la dernière image en vignette ; un fichier disparu reste, grisé, marqué *gone* ; un clic ouvre le fichier dans la colonne de lecture ; la carte lit et ne copie, ne déplace ni ne supprime jamais rien) ; *Published* (les URL `https://` des réponses des threads, dédoublonnées, classées — artifact claude.ai, PR, issue, commit GitHub, autre — avec l'hôte ; un clic ouvre le navigateur) ; *Checkpoints*. Fermée, son résumé dit `REPORT.md · 3 files · 1 page` (les parts non vides), sinon `N checkpoints`, sinon *nothing yet*. Elle se recalcule quand un tour se ferme ou que le sandbox change ; tailles et dates sont lues hors du thread principal. Seuls les threads ouverts comptent : l'activité d'un thread fermé n'est pas gardée. Fermée, une carte ne coûte qu'une ligne dont l'en-tête porte son résumé (`+108 −12`, la branche et son retard, l'état des checks et l'âge de leur lecture — `✓ checks passed · 4 min ago`, en gris passé trois intervalles de relecture (15 min) — le nombre de fichiers). Ce qui est un état reste visible dans l'en-tête (le mode de Changes, le repo de Repository, *Pull* quand la base est en retard, *Fix Conflicts*) ; les actions (rafraîchir, éditeur, shell, Finder) apparaissent au survol. Plusieurs cartes peuvent être ouvertes : les listes se partagent la hauteur, la séparation entre deux listes ouvertes se tire ; un double-clic leur redonne la même hauteur. Les cartes ne contiennent que des listes : le diff et le fichier de base s'ouvrent dans une colonne de lecture à part, entre la scène et l'inspecteur, sur toute la hauteur — l'équivalent de la zone d'édition de VSCode. Elle partage par défaut 50/50 la largeur laissée au terminal, se tire (la proportion est gardée), s'ouvre sur un geste (clic sur un fichier, `j`/`k`, un résultat de recherche, un lien du terminal) et se ferme d'un ✕ ou d'Échap. La même colonne porte le **pane Shell** de la task (`⌃\``, l'entrée *Shell* du menu Task et de la palette) : un shell de connexion (`$SHELL`) dans le dossier de travail de la task, avec les `SCOPE_*` qu'un thread reçoit (SCOPE_TASK, SCOPE_TASK_ROOT, SCOPE_PORT, SCOPE_HOME, SCOPE_SOCK…) moins SCOPE_THREAD — ce n'est pas un thread : rien dans la sidebar, rien sur disque. Des onglets pour plusieurs shells (`+` en ouvre un, ✕ le ferme ; l'onglet porte la commande en cours quand le terminal la signale, sinon le nom du shell), un pied qui dit ce qui est injecté. `⌃\`` le montre et le cache ; `⌘D` passe au diff et `⌃\`` revient au shell, le bouton retour aussi. Le ✕ du pane le cache sans arrêter les shells ; fermer un onglet, archiver ou fermer la task les arrêtent (SIGHUP, puis SIGKILL). À côté, le **pane Browser** de la task (`⌃⇧B`, le globe de la barre, *Browser* du menu Task et de la palette) : une `WKWebView` sur les serveurs de dev de la task. Un onglet par serveur (un lien vers un serveur déjà ouvert navigue dans son onglet ; une page qui ouvre une fenêtre ouvre un onglet), une barre d'adresse (URL, `localhost:3000` ou `:41001`) avec précédent / suivant / recharger, `⌘L` `⌘R` `⌘[` `⌘]` quand la page a le clavier, une étiquette *task* quand l'adresse est un port du bloc, un message qui dit de lancer le serveur avec `--port $SCOPE_PORT` quand rien n'écoute. Les pages sont inspectables (`isInspectable` : Safari ▸ Développement ▸ ce Mac). Cookies et stockage vont dans un *store* WebKit propre au scope (`WKWebsiteDataStore(forIdentifier:)`, UUID v5 du home et du scope : `BrowserStoreID`), persistant, séparé de Safari et de tout store d'agent. Routage (`BrowserRoute`, pur et testé) : un lien non `http(s)` ou sans task va au système ; sinon la préférence *Open web links in the pane* (Réglages › Général › Browser : les ports de la task, tout `localhost` — défaut —, tout le web, rien) décide, et `⌥`-clic envoie vers l'autre destination. Il s'applique aux puces de port, au `⌘`-clic dans un thread ou un shell et aux liens des réponses. Masquer le pane garde les pages ; fermer l'onglet, archiver ou fermer la task détruit les vues. Le pied porte une *Console* (ce que la page a logué, erreurs comptées en rouge). **Les agents de la task** ont leur onglet : `scope_browser_open` / `_read` / `_screenshot` / `_console` (et `scope browser …`, la même méthode `browser` du protocole) pilotent un onglet *agent* sur un store propre à la task (`BrowserStoreID.agent`, UUID v5 du home et de la task), supprimé à l'archivage avec ses captures. Un agent ne pilote que le navigateur de sa task (`AutomationPolicy.mayDriveBrowser`), un agent hors Scope aucun. L'onglet s'ouvre sans rien changer à l'écran ; dans le pane, il est marqué *Agent ·*, encadré en violet (`origin-agent`) sous un bandeau qui nomme le thread et sa dernière action. *Open* sans URL va au premier serveur de la task : un port du bloc en écoute, sinon un port hors bloc d'un de ses processus (hors plage éphémère), sinon `.claude/launch.json` (`LaunchConfig`), sinon `SCOPE_PORT` ; les ports hors bloc deviennent aussi des puces. *Read* lit la page depuis un monde isolé (`WKContentWorld` « scope ») : blocs de texte et éléments interactifs avec refs (`e12`), encadrés `<untrusted-page origin=… title=…>`, texte invisible marqué `(hidden)`, balise fermante de la page désamorcée, 50 000 caractères au plus (`BrowserPage.render`). *Screenshot* écrit un JPEG ≤ 1280 px sous `SCOPE_HOME/browser/shots/<task>/` ; `scope mcp` lit le fichier et le renvoie en contenu image (le socket plafonne à 1 Mio, pas de `structuredContent` en double). *Console* rend les lignes depuis le dernier appel, encadrées `<untrusted-console>` ; le relais vit dans le monde de la page, qui peut le neutraliser. **L'agent agit** : `scope_browser_click` (un ref de *read*, clic DOM, `isTrusted` faux : popups, sélecteur de fichier, presse-papier et plein écran n'aboutissent pas, la description le dit), `scope_browser_type` (focus, `insertText` qui déclenche les événements `input` que les frameworks écoutent, repli sur le setter natif ; `clear`, `submit` qui soumet le formulaire comme Entrée), `scope_browser_wait` (un sélecteur visible, un texte, ou une page qui ne charge plus et ne demande plus rien depuis 500 ms ; 10 s par défaut, 30 au plus), `scope_browser_network` (URL, type, durée depuis la timeline des ressources ; statut et méthode seulement pour fetch/XHR, lus par une enveloppe dans la page, falsifiable ; encadré `<untrusted-network>`). Les refs vivent dans une table du monde isolé, retenu par l'app (WebKit oublie un monde que personne ne retient, et ses globales avec). Réglages › Automation › Browser : *Acting in a page* (approbation `browser`, allow/ask/deny, `allow` par défaut ; lire, capturer, la console, le réseau et attendre ne demandent jamais), *Agents may browse* (`browserSites` : les ports de la task, localhost, partout — défaut), *Blocked sites* (`browserBlocked`, sous-domaines compris). `open` refuse d'avance ce qui sort de ces règles ; pour le reste, une `WKContentRuleList` compilée depuis `BrowserSitePolicy.contentRules` (tout bloquer, puis `ignore-previous-rules` pour ce qui est permis, une règle par alternative : le `url-filter` de WebKit n'a pas de `|`) bloque navigations et sous-ressources de l'onglet agent. Quand une page de l'agent va hors localhost, une carte non bloquante le dit (*The agent opened js.stripe.com*) avec *Block … for This Task* (liste de la task, gardée tant que l'app tourne). Le bandeau agent porte **Stop** (Échap tant qu'un appel tourne) : les appels en cours s'arrêtent, les suivants sont refusés (*the user stopped the browser*) jusqu'à *Let It Continue*. Le pied de l'onglet agent porte *Actions*, le journal des actions (heure, action, cible, issue, thread). Un téléchargement (ce que WebKit ne sait pas afficher, ou `Content-Disposition: attachment`) va sous `SCOPE_HOME/browser/downloads/<task>/`, jamais dans les dossiers de l'utilisateur ; le pied le montre, un clic le révèle. La carte *Plan* montre ce que l'agent compte faire et où il en est, en direct : pour chaque thread vivant de la task qui en a un (son titre en étiquette quand il y en a plusieurs), le titre du plan puis une ligne par étape — cercle vide en attente, cercle pointillé à la couleur d'accent avec la forme active (« Running the tests ») pendant qu'elle tourne, coche verte une fois faite, barrée ; l'étape courante en encre primaire ; au-delà de huit lignes, *Show all N*. Fermée, elle dit `3/7 steps · <étape courante>` ou *no plan yet*. Pour une task *mission*, les jalons viennent d'abord, et le jalon courant s'ouvre sur les étapes du thread qui le fait. Le plan vient des hooks, sans lire le transcript : `PostToolUse` de `TodoWrite` (la liste remplacée), de `TaskCreate` / `TaskUpdate` / `TaskList` (une tâche à la fois, par id), d'`ExitPlanMode` (titre = premier titre du markdown, étapes = ses éléments numérotés ou à cocher), et les hooks `TaskCreated` / `TaskCompleted` ; toute autre entrée de la même forme (un tableau d'objets avec un texte et un statut) est lue aussi, une forme inconnue est ignorée. Il est gardé dans le fichier d'activité du thread et survit à un redémarrage. Les versions récentes de Claude Code ne proposent plus ces outils aux modèles récents par défaut : les profils *Claude Code* et *Claude Code (bypass)* fournis posent `CLAUDE_CODE_ENABLE_TODO_TOOLS=1` pour que la carte ait de quoi se remplir. Dans la sidebar, une ligne qui porte sa deuxième ligne finit par ` · 3/7 steps` tant que le plan a des étapes à faire — jamais une icône ni une seconde marque à droite. Sans task il n'y a qu'une page, celle de la base checkout (Repository, Files, Search, History), sans bouton Details ; les cartes de task n'y sont pas. La carte *Connectors* est **masquée par défaut** — elle a encore peu à montrer — et le menu *Cards* la fait apparaître ; une place mémorisée avant elle la garde masquée (la place retient les cartes qu'elle connaissait). Elle liste les serveurs MCP des threads Claude Code vivants de la task, tels que `ClaudeMCPServers` les tient de leur transcript et de leur configuration : un glyphe de prise, le nom, `· user · stdio` (source et transport) en tertiaire, à droite `12 tools · 3 calls` puis l'état — point teal quand ses outils sont listés ou appelés, couleur d'attente pendant la connexion, rouge avec le code d'erreur (le message en bulle) quand il a échoué, gris *not reported* quand Claude Code n'en a rien dit, et une pastille *re-authenticate* couleur d'avertissement quand il attend une connexion : elle n'envoie rien, sa bulle dit de taper `/mcp` dans le thread, un clic amène ce thread au premier plan. Les ennuis d'abord (authentification, échec, connexion en cours), puis les connectés par nom ; au-delà de dix lignes, *Show all N*. Une seule liste quand les threads s'accordent, un groupe par thread sous son titre sinon. En pied : *Read from Claude Code's transcript and configuration · never edited by Scope*. Fermée, elle dit `3 · 1 needs auth`, `4 · 2 failed`, `3` ou *none* ; une task sans thread Claude Code dit que la carte ne connaît que Claude Code. Au repos, Environment et Changes sont ouvertes avec une task, seule Repository sans ; Files est fermé et son arbre s'ouvre tous dossiers fermés (un saut de recherche n'ouvre que les dossiers du fichier). Les cartes ouvertes et masquées sont mémorisées par scope, séparément avec et sans task. `⌘D` / `⌘⇧B` ouvrent et focalisent leur carte, sans jamais la refermer, en passant à la page où elle se trouve. Le *Graph* et la liste des pull requests du scope sont des feuilles ouvertes depuis la sidebar. Les boutons *Commit*, *Push*, *Créer la PR* et *Merge* sont masqués par défaut : c'est le travail de l'agent dans son thread, le panneau sert à lire ce qu'il a fait. La carte *Context* se termine par une **frise de la task** depuis sa création : trois nombres (temps d'agent, toutes les lanes additionnées ; temps d'attente de toi — question, permission, résultat non lu, compté une fois quelle que soit la lane ; temps écoulé), puis une lane par thread (fermés compris : leurs tours sont gardés dans `tasks/<id>.timeline.json` quand le thread se ferme) avec ses tours en barres, les attentes entre deux en bandes teintées, les tours échoués en rouge, et les événements de la task en traits (création, PR ouverte, checks rouges ou verts à chaque changement, merge, archivage). Les heures creuses (plus d'une heure sans aucun tour ni événement) se replient en une coupure de largeur fixe libellée `⋯ 9 h`, au plus une par 48 pt de largeur et jamais plus de la moitié de la frise ; une attente traverse la coupure, rétrécie. Survoler une barre dit quand, combien de temps, comment le tour s'est terminé et les premiers mots de la réponse. La carte de survol d'une task en montre une version plate (les nombres et toutes les lanes sur une bande). `scope summary` et `scope_summary` donnent les deux temps par task ; une task fermée les laisse dans l'historique.- **Palette** `⌘K` : nouveau thread, nouvelle task, ajouter un repo à la task, ouvrir `<repo>` dans l'éditeur, ouvrir la task dans l'éditeur, analyser le graph, aller à un thread, déclarer un scope. Sur la task courante : l'archiver, la classer sous un topic ou l'en sortir, ouvrir sa pull request, copier sa branche ; *Restore Archived Task…* liste les tasks archivées du scope. Aucune confirmation : archiver ne perd rien. *Ask Orchestrator…* (`⌘⇧K`) transforme la palette en champ de message adressé à l'orchestrateur du scope (`↩` envoie, `⇧↩` va à la ligne) ; *Send to Thread…* choisit d'abord un thread dans la même liste que *Go to Thread*. Le texte part comme un `thread.send`, sans signature puisqu'il vient de l'utilisateur ; un thread arrêté est démarré pour le recevoir, et le message attend que le driver lise son entrée. La sélection et le terminal ne bougent pas ; un toast *Sent to <scope> orchestrator* offre *Show*. Une recherche qui ne trouve rien, ou qui se lit comme une phrase (trois mots ou plus), propose en dernière ligne *Ask Orchestrator: <texte>* : `⌘K`, taper, `↩` suffit.
- **Répondre sans changer de thread** : `⌥↩` sur une ligne de la sidebar (quand la liste a le clavier) ou *Reply…* dans son menu contextuel ouvre un champ sous la ligne, précédé des dernières lignes de la réponse de l'agent (rien si elle précède le dernier prompt). Mêmes touches que la palette, `Esc` referme. Pas pendant qu'un tour est en cours.
- **Raccourcis** : `⌘O` déclarer un scope, `⌘T` nouveau thread, `⌘⇧T` nouvelle task (ou rouvrir le dernier thread fermé), `⌘Z` annuler la dernière fermeture ou archive (30 s), `⌘W` fermer le thread, `⌘E` / `⌘⇧E` éditeur, `⌘D` changes, `⌘⇧B` repository, `⌘1..9` threads, `⌃1..9` scopes (dans l'ordre déclaré), `⌥⌘←` / `⌥⌘→` scope précédent / suivant, `⌃⌘S` sidebar, `⌃⌘L` lignes détaillées ou compactes, `⌃⌘G` rangement en arbre ou par état, `⌘⇧K` demander à l'orchestrateur, `⌥↩` répondre depuis la sidebar, `⌘⇧R` lire la réponse de l'agent, `⌘⇧I` l'Inbox ; depuis n'importe quelle app, `⌥Space` le panneau rapide et `⌥⇧Space` la fenêtre. **`⌘` maintenu seul** une demi-seconde affiche le raccourci de chaque contrôle qui en a un dans une petite pastille à côté de lui — boutons de la barre d'outils et de la sidebar, lignes de thread (`⌘1…9`, `⌥↩`), tuiles de scope (`⌃1…9`), en-têtes Delta et Base, `j`/`k` et `[`/`]` sur le diff, `⎋` sur la colonne de lecture — et le relâcher les cache ; une touche ou un clic avant le délai (`⌘C`, `⌘`-clic sur un lien) annule, un raccourci tapé pendant l'affichage s'exécute normalement. La détection et la lecture des équivalents clavier sont des fonctions pures de ScopeKit (`CommandHoldDetector`, `KeyEquivalentText`), testées. ## 8. Non-objectifs v1

- Pas de chat UI, pas de wrapper autour des agents.
- Pas de client git complet (rebase interactif, conflits : on ouvre l'éditeur).
- Pas de sync cloud, pas de multi-utilisateur, pas de Linux/Windows.
- Pas d'orchestration entre threads (un thread ne pilote pas un autre).
- Pas de gestion de secrets, pas d'isolation process.
- CLI `scope` complète (déclarer un scope, lancer un thread depuis le terminal) : après v1, sur la base de `scope-hook`.

## 10. Décisions ouvertes

1. **`~/.scope/` vs Application Support** pour tout ce qui est visible en terminal (proposé : `~/.scope/`, surcharge `SCOPE_HOME`).
2. **Emplacement des sandboxes** par défaut : `~/.scope/sandboxes/` (proposé) ou à côté des repos, en opt-in par scope.
3. **Cwd par défaut d'un thread** : task (proposé) ou racine du scope ?
4. ~~**Nom de branche** : `scope/<slug>` ou `<user>/<slug>` ?~~ Tranché : la convention du repo, proposée par le driver ; `scope/` réservé.
5. **Base de branche** : `origin/<default>` fraîchement fetché (proposé) ou la base locale ?
6. ~~**Projection mono-repo** : flag de contexte du driver, ou fichier + `.git/info/exclude` ?~~ Tranché : fichier + `exclude`, écrit dans le cwd des threads, sous chaque nom déclaré par les drivers ; un fichier que Scope n'a pas généré est laissé en place et signalé.
7. **Rendu du delta** : natif SwiftUI + parser (proposé, cohérent, plus long) ou `WKWebView` + diff2html (rapide, moins natif).
8. **Graph L1** : quel driver par défaut ? Coût et durée acceptables par repo ?
9. **Repos non clonés** : `gh` obligatoire, ou API GitHub avec token ?
10. ~~**Setup post-sandbox** : commande dans le graph (proposé) ou détection depuis les manifestes ?~~ Tranché : commande de la carte du graph (éditable), surchargeable par repo dans la config du scope, avec un `teardown` symétrique ; Scope n'écrit rien dans les repos pour ça.
11. **Scopes imbriqués** : autorisés (proposé) ou refusés ?
